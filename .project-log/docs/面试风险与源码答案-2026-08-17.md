## 1. 视觉引导切豆腐机器人（2026.04–2026.05）

### 1.1 “90%+ 成功率怎么统计？”

**一句话口径（建议）**
> “完整流程成功率”指的是：从抓刀完成 → 视觉定位 → 三刀切割 → 人工两次旋转后重新定位 → 切完的目标场景。我在调试期的主流程实机验证达到 90%+；当时按‘豆腐被切成目标数量/形状、无刀具碰撞、任务状态机正常走完’判定成功。仓库里没有把每次测试逐条落盘，所以我不会把 90% 说成严格统计实验，而是开发期连续验证的工程口径。”

**源码能证明的边界**
- 成功路径有明确 7 阶段状态机：`phase_manager_node.py` 中 `PHASE_1_GRAB_KNIFE → PHASE_2_MOVE_TO_PREPARE → PHASE_3_FIRST_CUT → PHASE_4_ROTATE_TOFU → PHASE_5_SECOND_CUT → PHASE_6_ROTATE_TOFU → PHASE_7_THIRD_CUT → DONE`（`cuttofo_xcore/cuttofo_xcore/phase_manager_node.py`）。
- 存在“豆腐倒没倒”的视觉检测分支设计：`tofu-fall-detection.md` 定义 5 个特征（倾斜角、右下占用、高点残差、边缘扩展、可见率），说明“成功”不是只看状态机走到 DONE，还包括豆腐是否被有效切倒。
- **仓库中没有测试次数/失败类型的逐次记录**。面试前建议自己补一张小表：测试日期、环境（固定工位？）、次数、成功数、失败原因（视觉漏检/IK 不可达/TCP 偏/运动超时等），不需要多，5–8 次口径即可。

**失败类型（源码里能找到的已知问题）**
- IK 可达性：`prepare_pose_selector.py` 专门做多候选 IK + 安全关节边界 + 切割轨迹预览，就是为了过滤“预备位能解但下切路径不可行”的情况。
- TCP 坐标冲突/手眼标定误差：`cuttofo_calibration` 记录中有 RMSE 评估；`docs/PROJECT_LOG.md` 记录过 TCP 冲突修复。
- 竖直切的小问题：备份目录名“竖着切有点小问题”本身就是实机暴露点。

### 1.2 “自研视觉算法具体自研在哪里？”

**一句话口径**
> “SAM3 是复用的分割模型，我自研的是‘拿到分割 mask 之后到机器人可执行 TCP 目标’这一段：点云清洗 → 豆腐顶面约束 OBB 拟合 → 顶面四角重建 → 长边方向 → 刀具 TCP 目标与姿态约束 → 候选位姿评分。也就是把基础模型输出变成机器人能执行的目标，这段全部是我写的。”

**源码链路（按顺序讲）**
1. `SAM3DetectorNode`（`dexbot_middle_layer/.../sam3_detector_node.py`）只做分割 mask，是基础资源。
2. `pose_estimator_node.py` 用 `get_pose_from_mask`（`vision/pipeline/vision_utils.py`）把 mask + 深度图变成带姿态/尺寸的对象：
   - `clean_point_cloud`：voxel 降采样 → 统计离群点去除（SOR）→ 半径离群点去除（ROR）→ DBSCAN 最大簇；
   - `fit_constrained_obb_xz`：**只绕垂直轴（yaw）穷举 0.5° 步长搜最小面积 OBB**，再用百分位边界确定长/短轴和顶面高度（豆腐是规则长方体，yaw-only 约束比通用 OBB 稳）；
   - 输出 `(T_base_obj, top_corners, extents, angle)`。
3. `tofu_state_node.py` + `tofu_geometry.py`（自研核心）：
   - `reconstruct_corners`：由 中心+四元数+尺寸 重建 8 角点；
   - `extract_top_corners`：按 Z 最高的 4 个角点取豆腐顶面；
   - `compute_edge_dir`：按长边方向确定切刀需对齐的边方向；
   - `compute_tcp_target_from_corners`：用顶面四角计算 TCP 落点（中点 + `offset_a=0.03` 侧向偏移 + `vertical_offset=0.03` 抬起高度）；
   - `build_rotation_with_edge_dir`：由边方向 + 平面倾角（如 40°）构造刀具姿态旋转矩阵；
   - 平滑：`smoothing_alpha=0.4` 指数平滑位置/尺寸/TCP，`valid_timeout=2s` 超时置失效。
4. TCP 目标到机器人：`prepare_pose_selector.py` 离线 IK 求解 + 预览 + 评分（见 1.3）。

**可以主动强调的点**
- SAM3 只给 mask；**豆腐四角、边方向、TCP 目标、刀具姿态、候选评分都是几何/机器人工程逻辑，不是模型能力**。
- 深度点云清洗参数（voxel 2mm、SOR、ROR、DBSCAN）是为了抗深度噪声/桌面干扰，面试可以讲为什么需要（豆腐表面反光/深度边缘毛刺）。

### 1.3 “IK 候选怎么求解和评分？”

**源码依据：`cuttofo_lbot/cuttofo_lbot/prepare_pose_selector.py`（xCore 版同逻辑）**
- 用 `OfflineURDFKinematics` 解析真实 URDF（`ar5_07r_w4c1c1_description/urdf/AR5-5_07R-W4C1C1.urdf`），7 自由度右臂。
- 候选生成：`solve_prepare_candidates` 用当前关节角 + 安全边界内的随机扰动（`N(0, 20°)`）做多种子，`least_squares` 求解，残差 = 位置误差 + 旋转误差（`rotvec`）+ 归一化关节中心偏差。
- 硬约束：位置容差 `POS_TOL_M=1e-4`（0.1mm）、旋转容差 `ROT_TOL_RAD=0.06°`、关节不越界；`make_safe_bounds` 在原始限位内再缩一个安全裕度。
- 评分：`rollout_cut_preview` 把每个预备候选沿“下切方向”做几步 IK 前瞻，`score_preview_trajectory` 加权：
  `total = 1.0×path_cost + 5.0×jump_cost + 3.0×joint1_cost + 0.001×limit_cost + 0.02×wrist_cost + 0.01×current_cost`
  - `path_cost`：路径总位移平方；`jump_cost`：最大单步跳变（防突变）；
  - `joint1_cost`：肩关节 1 尽量少动；`limit_cost`：越接近限位惩罚越大（1/裕度²）；
  - `wrist_cost`：手腕关节（5/6）尽量小；`current_cost`：离当前位姿尽量近。
- 面试表达：**“我不是只看预备位能不能解，而是把每个候选继续往下切方向滚一遍，选路径平滑、离限位远、手腕不别扭的那个”**。

### 1.4 “手眼标定 / TCP 标定怎么做的？”

**源码依据：`cuttofo_calibration`（Tkinter 手眼标定 GUI）**
- 眼在手外（eye-to-hand）：相机固定，ArUco 标定板装在机械臂 TCP 末端；拖动示教采样 10–30 个姿态，同时记录 `TCP 位姿 + ArUco 位姿`，用经典手眼标定求解 `T_base_cam`。
- 设计上有内参标定（ChArUco）与手眼标定两条流水线：`charuco_detector.py / charuco_capture_node.py / charuco_handeye_solver`（见 README 与 `.project-log/requirements.md`）。
- TCP 偏移标定：`calibrate_tcp_offset.py` + `architecture/tcp-offset-calibration.md`，多姿态对准同一尖端，最小二乘求 `p_tcp`。
- 结果使用：`T_base_cam` 写入 `calibration_result.yaml`，视觉目标先转到 base 坐标系再做机器人运动。

### 1.5 其他可能追问
- **为什么用 7 阶段状态机**：抓刀/预备/切割/人工旋转/再切割之间需要明确的等待屏障（旋转后要重新视觉定位），状态机让每一阶段可单测、可跳过（`start_phase` 参数可从任意阶段切入）。
- **如何容错**：视觉超时 `valid_timeout`、相位 `PHASE_ERROR`、`pose_estimator_node/reset_state` 服务、`tofu_geometry` 中边方向退化回退（`v.x≈0` 处理）。

### 2.2 “Policy 和 Skill 的职责边界？完整阶段序列？”

**源码依据：`kitchen_robot_home/src/dexbot_task_planner/dexbot_task_planner/policy/pan_pour/pan_pour_policy.py` + `robot_motion_executor/.../skills/pan_pour/pan_pour_skill.py`**

### 2.3 “锅把感知怎么转成抓取目标？坐标系怎么算？”

**源码依据：`perception_adapter.py` + `entities/pan_pour_kinematics.py`**
- `perception_adapter.py`：从 `ScenePerception` 取 `pot_handle_center` 和 `pot_inner_handle` 两个类别，用中心−根部得到锅把方向（PCA 轴），抓取点为 handle center，输出到 center 坐标系。
- `pan_pour_kinematics.py`：`RigidTransform` 纯 SE(3) 模块；核心公式（工程记录原文）：
  `T_B_F = T_B_C @ T_C_TCP @ inverse(T_F_TCP)`
  - `T_B_C`：base→中心坐标系（由左右臂标定 + `generate_robot_center_frames.py` 生成）；
  - `T_C_TCP`：中心坐标系下的锅具 TCP（含 TCP 标定）；
  - `T_F_TCP`：法兰→TCP 偏移（`pan_pour_params.yaml` 的 `flange_to_tcp.translation`）。
- `pan_pour_params.yaml` 有 `configured: false` 门禁：未标定配置不允许执行，避免拿错误外参跑真机。

### 2.5 “增量倾倒回放是什么？为什么用增量？”

## 3. 机器人数据管理与质检平台（2026.05–2026.07）

### 3.1 “290 万 episode_objects 怎么管理？为什么 MinIO + PostgreSQL 分层？”

**一句话口径**
> “MinIO 是原始对象事实源，PostgreSQL 是业务控制面。对象不重复存两份，控制面只保存 List/Batch/EpisodeInventory/EpisodeObject 的元数据与状态，对象本体仍在 MinIO；每次扫描从 MinIO 流式枚举并与控制面指纹对比，实现‘发现→索引→QC→决策→导出’。”

**源码依据**
- 模型：`software/backend/app/models/control_plane.py`（`ScanJob/ScanShard/ScanPrefixState/DiscoveredPrefix/ListRecord/EpisodeInventory/EpisodeObject/...`）、`batch.py`、`episode.py`、`qc.py`。
- 设计文档：`software/docs/scan-architecture-final-plan-v3.md`——生产快照 `episode_objects = 2,909,780`；最终方案不新增 `object_inventory` 表，复用 `episode_objects` 的 `(object_key, etag, size_bytes, last_modified)` 指纹判断变化。
- 分层原因：对象数量大（百万级），不能靠一次 `list(...)` 全量进内存；业务状态（QC、导出、资产投影）需要可查询/可审计，放 DB；原始数据流和业务控制面解耦后，扫描失败不会污染对象本体。

### 3.2 “四种扫描模式（smart/full/incremental/manual_prefix）？”

**源码依据：`services/scan_queue.py` `create_or_get_scan_job` + v3 文档**
- `smart`：前端主按钮/每日默认；先 namespace discovery，只扫新 List、待确认缺失、失败重试和到期 List；若 7 天内没有成功 full 自动升级 full。
- `incremental`：缩小 List 范围、只解析变化 Episode（不是 MinIO 变更日志）。
- `full`：完整 discovery + 所有 List 分片，忽略 `next_scan_at`；仍按 List 分片，禁止全桶 `list(...)`。
- `manual_prefix`：管理员定向重扫指定 prefix（排查/上传后立即同步）。
- 幂等：同一 bucket 同时只允许一个 active job；重复点击返回现有 job（`create_or_get_scan_job` 先查 active）；shard 用 `shard_key` 去重。

### 3.3 “并发 worker 怎么保证不重复、不丢任务？（SKIP LOCKED / lease / heartbeat）”

**源码依据：`services/scan_queue.py` + `scan_worker.py` + `scan_coordinator.py`**
- 取任务：`claim_next_shard` 在 PostgreSQL 上用 `with_for_update(skip_locked=True, of=ScanShard)`，同一 shard 只被一个 worker 抢到；抢到后写 `lease_owner / heartbeat_at / lease_expires_at`。
- 心跳：worker 循环里 `heartbeat_shard` 定期续租（`scan_worker_heartbeat_seconds`），避免长任务被误回收。
- 回收：coordinator `reclaim_expired_leases` 把 `lease_expires_at < now` 的 running shard 重置为 `retry_wait`（`next_retry_at` 按 `RETRY_DELAYS_SECONDS=(30,120,600)`、`max_attempts=3` 重试）。
- 发布前检查：`_lock_owned_shard` 校验 lease 仍归自己，否则抛 `lease was lost before publication`，防止过期 worker 写脏结果。
- 取消/恢复：`cancel_requested_at` 阻止新 claim；重启后 `pending/retry_wait` 继续执行，过期 running 被回收重试；`repair_bad_event_tail` 之类的状态修复思路也用于任务日志。

### 3.4 “missing / recovery 怎么做？会不会误判删除？”

**源码依据：`services/scanner.py` + `models/control_plane.py`**
- 对象带 `source_status`（`present/missing`），上次确认过、本次没看到的 List/Episode/对象**不直接删除**，先置 stale/缺失状态，等后续扫描确认。
- `_apply_state_transition(existing_state, next_state)` 统一管理状态迁移；恢复路径：对象重新出现 → 恢复为 present，业务资产可重建（`data_assets.py` 的 recompute 队列：`BatchAssetRecomputeJob → BatchAssetRollup → TaskAssetRollup`）。
- 为什么要这么设计：全量枚举中断/瞬态网络错误不能把“没扫到”当“被删了”；这也是 v3 放弃“扫描不完整即删除”方案的原因。

### 3.5 “QC 状态和 QUALIFIED 怎么流转？”

**源码依据：`services/batch_adjudication.py` + `dataset_service.py` + `models/episode.py`**
- 每个 Batch 抽样 `sampled_episodes`，人工 QC 标记 `MANUAL_PASS / MANUAL_FAIL`。
- 抽样的都审完才裁决（`reviewed_count < sampled_count` 不裁决），失败率 `fail/sampled > reject_threshold` → 批次拒绝，否则通过。
- 裁决是幂等的：重复执行结果一致（`adjudicate_batch` 注释明确 “Idempotent — re-running produces same outcome”），并写 `BatchDecisionLog` 审计。
- Episode 最终状态 `final_dataset_status = QUALIFIED / UNQUALIFIED`，`is_exportable` 据此设置；导出 `DatasetExportService.export_episodes`（CSV）只取 QUALIFIED，`record_export` 写审计。
- 设计要点：**批次裁决是抽样统计决策，单条 episode 的 final status 由裁决规则推导**；批量驳回可覆盖人工 PASS（`BATCH_REJECT_OVERRIDE_MANUAL_PASS`）。

### 3.6 “8 个 active List 和 58 个 active List 怎么对不上？”

- `software/docs/scan-architecture-final-plan-v3.md` 记录 2026-07-17 生产快照：58 active List / 5,987 Episode Inventory / 2,909,780 episode_objects。
- 简历材料记录用户确认的当前口径：8 个 active List / 3,987 Inventory / 一次真实扫描 42 List、4,097 Episode。
- 建议面试口径：**两个数字是不同时间点的快照口径**。58/5987/290万 是 7 月架构基线（当时对象索引迁移前）；8/3987 是当前正常生产维护状态；42/4097 是某次真实扫描任务的验收结果。具体以你现场能查到的最新数字为准，并准备好说“存量 List 已归档/下线，所以 active 数变化”。

## 4. GR00T N1.7 策略模型训练与部署（2026.07–至今）

### 4.1 “MSE 从 717 降到 13 是怎么回事？”

**源码依据：`docs/gr00t-engineering-report.md`、`docs/gr00t-code-deep-dive.md`、`.project-log/progress.md`、`verification` 记录**
- 指标口径：`open_loop_eval.py` 在**训练集** 4 条轨迹上，每轨 400 步、`execution_horizon=16`、4 次去噪，比较模型预测动作与记录动作：
  - 新 checkpoint-30000：MSE 13.73 / 18.50 / 29.87 / 22.50，平均 **23.62**；MAE 平均 **1.15**；
  - 旧 20k checkpoint（traj 0）：MSE **717.38**；
  - 相对旧 checkpoint 改善约 98%，相对 current-state baseline 改善约 83%；训练末 batch flow-matching loss 约 0.038。
- 为什么 717 → 13：不是玄学，是**训练暴露量不够**：
  - 旧 20k 训练约 0.44 effective pass（数据没被充分学习）；
  - 新 30k + batch=1 + `gradient_accumulation_steps=8`：`30000 × 8 / 45030 ≈ 5.3` 个全量 pass（`docs/gr00t-code-deep-dive.md`）。
- 单位说明：MSE 作用在**归一化动作空间**（processor 先 `(x-mean)/std` 归一化，decode 时反归一化），所以数字没有“弧度/毫米”这种物理单位；MAE=1.15 也是归一化空间。面试要主动说明“两个模型在同一个 eval 脚本、同一 4 条轨迹、同一归一化空间下对比”。

### 4.2 “数据怎么转的？13D embodiment 是什么？”

**源码依据：`convert_to_lerobot_right_o6.py` + `gr00t_n1/examples/linkerhand_right_o6_config.py`**
- 数据：148 episodes、47,250 帧、3 路相机（cam_top / cam_left_wrist / cam_right_wrist），任务标签 `pouring`。
- 转换校验：`scan_episodes` 检查 manifest frame_count == telemetry 帧数、相机时间戳严格递增、`ffprobe` 视频帧数与时间戳一致，不一致整集跳过。
- 13D：`STATE_DIM=13` = 右臂 7D 关节 + O6 灵巧手 6D 角度；`right_arm [0:7]`、`right_o6_hand [7:13]`，O6 原始值乘 `O6_RAW_TO_SDK_ANGLE` 转 SDK 角度。
- 元数据：features/state names/splits/video info 按 LeRobot v3.0 契约写入 `meta/`（`codebase_version: v2.1` 为源数据版本，目标格式是 LeRobot v3.0）。

### 4.3 “Normalization 怎么做的？”

- 训练前必须生成 `meta/stats.json`（`gr00t/data/stats.py`），finetune 脚本启动时强制检查。
- Processor 流程：观测/动作先减 mean 除 std 归一化 → 13D padding 到 132（action_mask 盖掉多余 119 维）→ 模型输出 → `decode_action` 反归一化。
- 面试可以讲：**归一化是训练稳定性的前提**，7D 关节弧度（量级 ~0.1–3）和 6D 手指角度（0–100）量纲差很多，不归一化会劣化扩散模型学习。

### 4.4 “为什么 30k / batch1 / accum8 / RTX 4090？”

- `finetune_right_o6_13d.sh`：`NUM_GPUS=1`、`global_batch_size=1`、`gradient_accumulation_steps=8`、`gradient_checkpointing`、`paged_adamw_8bit`、lr=5e-5 constant、warmup=1500。
- 目的：单卡 24GB 显存约束下，用显存换有效 batch；8 步累积近似 batch 8 的优化器更新。
- 面试表达：**global batch 保持 1 是显存限制，accum=8 让每次 optimizer step 等价于 8 条样本梯度，30000 step 才对应约 5.3 次全量数据 pass**。

### 4.5 “Open-loop 能证明什么？不能证明什么？”（必答）
- 能证明：模型在**已见训练轨迹**的专家观测下，预测动作接近记录动作（MSE/MAE 降低）；说明接口、Processor、训练配置、暴露量是自洽的。
- 不能证明：未见轨迹泛化、仿真/真机闭环成功率、动作安全性、 pouring 任务成功。`gr00t-engineering-report.md` 原文明确写“该结论不包含‘模型能完成真实 pouring’或‘模型能泛化到新场景’”。
- 如果面试官问下一步：数据扩多样本 → 保留验证集 → 闭环仿真 rollout → 真机小范围验证 → 远端推理服务接入（基于组内已有 service_host 框架完成部署准备）。

## 5. Vibe Coding 可恢复 AI 工程工作流（个人作品，GitHub: TBLboy/vibe-coding）

### 5.1 “这是不是 AI 帮你生成的？你的贡献是什么？”

**一句话口径**
> “代码是用 Codex 辅助开发的，但‘解决什么问题、状态机长什么样、证据怎么算失效、失败怎么归因’这些设计决策和工程总结是我做的。这个项目的本质不是一堆 prompt，而是一套可执行的 Python runtime：project-log 结构、loopctl 状态机、证据失效 Hook、安装器和 20+ 个 Skills。而且它已经在切豆腐/老板电器/数据平台这些真实项目里用来恢复会话和定位失败。”

**源码证据（`vibe-coding/runtime/`）**
- `runtime/scripts/loop_state.py`（737 行）：`record_evidence / invalidate_evidence / evaluate_goal / sync_native_goal / generate_handoff / validate_loop`。
- `runtime/scripts/loopctl.py`：CLI 子命令 `restore / start / event / record-evidence / invalidate-evidence / goal-bind / evaluate / validate / handoff`。
- `runtime/hooks/`：`session_start.py`、`post_tool_use.py`、`pre_compact.py`；`post_tool_use` 会在写文件后自动把覆盖到文件的 evidence 标记 `stale` 并追加 `work-unit-finished` 事件。
- `scripts/global_installer.py` / `install.sh`：向用户级 AGENTS.md 注入主规则、安装 Skills、写 `vibe-python` 配置。
- `skills/a-loop-control/SKILL.md`：失败归因 9 类（implementation/specification/task-decomposition/technical-selection/functional-business-logic/technical-business-logic/environment/verification-harness/unknown），Retry Contract 要求 `retry-current-task` 带可证伪 hypothesis、delta、expected evidence。

### 5.2 “Project Log / Evidence / Retry Contract 具体怎么工作？”

- **Project Log**：每个项目 `.project-log/` 下固定结构（business-logic/requirements/tasks/decisions/verification/loop/...），目标、任务、证据、会话恢复都在文件里，不依赖聊天上下文。
- **Evidence**：`loop_state.py` 中证据状态 `candidate | valid | failed | stale | superseded | invalid`；记录时绑定 `version_binding`（覆盖文件的 SHA256）；文件被改 → `invalidate_evidence` 自动置 stale；`evaluate_goal` 只认可 `valid` 证据，且高/关键风险目标必须有独立 review 证据。
- **Retry Contract**：失败先归因到 9 类之一；重试必须说明新假设、变化量（delta）和预期证据；失败签名不变禁止盲目重试（全局 AGENTS.md 规则 + `a-loop-control` skill）。

### 5.3 “真实项目里怎么帮你恢复状态/定位失败的？”（准备 2 个例子）

**例 1：老板电器 SDK 版本兼容问题（`boss_electrics/.project-log/current-session.md`）**
- 现象：GUI 连左臂报 `xCore最低版本要求3.1.0.0`。
- 归因：不是网络/配置问题，是 PC SDK v0.7.1 内部 `xCoreRequired()=3.1.0.0` > 控制器 xCore `3.0.1.6`。
- 动作：验证旧 SDK v0.5.1 可连接 → 回退并同步修改全部路径引用 → 编译/导入验证。
- 这套“现象→归因→验证→回滚”记录就是 Vibe 工作流留痕的直接产物。

**例 2：老板电器直连 SDK 坐标系 90° bug（同一工程记录）**
- 现象：实机读回位姿与目标差 90°、位置误差 621.5mm。
- 归因：本地脚本缺左臂 `-90°` 输入补偿和 `EndInRefToFlanInBase` 转换，把外部法兰目标直接喂 `MoveL`。
- 修复：补 `_apply_input_frame_compensation / _end_in_ref_to_flange_pose`，离线验证 IK 与 MoveL 下发一致；同时检查正式链路确认无同类 bug。
- 这是“用工程记录避免把局部脚本 bug 误当成正式链路 bug”的典型例子。

**例 3（可选）：本项目自己**
- `My_knowledge_base/.project-log` 完整保留了 TASK-001~005 的状态、证据、会话恢复；本轮就是从 `.project-log` 恢复上下文后继续推进。

### 5.4 “Hook 生命周期？”
- `SessionStart`：会话开始时读取/恢复项目状态，记录会话启动事件。
- `PostToolUse`：工具执行后记录 `work-unit-finished`，写文件时自动 invalidate 受影响证据。
- `PreCompact`：上下文压缩前自动生成 handoff，避免压缩丢失状态。
- 安装器做三方合并升级，冲突在写入前停止（保护用户本地修改）。
