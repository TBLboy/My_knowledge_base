## 二、项目背景

### 2.1 平台定位

**Robot QC V1** — 灵机启物机器人数采质检平台。为 Linker Open TeleDex 机器人数据采集项目提供训练数据消费与数据资产供给。当前处于生产使用阶段，已有真实数据在平台上运行质检流程。

### 2.2 技术栈

| 层 | 技术 |
|---|---|
| 后端 | Python 3.12 + FastAPI + SQLAlchemy 2.0 + Alembic + APScheduler |
| 前端 | Vue 3 + TypeScript + Element Plus + Chart.js + Pinia + vue-router |
| 存储 | PostgreSQL 15（业务数据源，唯一事实源）+ MinIO（原始对象存储，仅对象读写） |
| AI | Ollama 托管 Qwen3-VL-32B-Thinking（Q4_K_M, 24GB 显存），用于 AI 质检解释（SSE 流式） |
| 部署 | Docker Compose（backend + frontend + scan-coordinator + scan-worker + db + minio） |
| 测试 | 独立 Python 脚本，无 test runner 配置 |

### 2.3 数据格式（每个 Episode）

每段演示数据（存储在 MinIO `yaocao/<task_list>/processed/episode_XXXXXX/`）：

| 文件 | 格式 | 内容 |
|------|------|------|
| `telemetry.npz` | NumPy `.npz` | 时序数据：timestamps(N,), qpos/qvel/effort/actions(N×D), ee_poses(N×7), IMU(N×6), sync_validation 等。D = 双臂7+7 + 双手6+6 = 26 维 |
| `cam_top.mp4` | H.264 MP4 | 头部 RGB 视频，640×480 |
| `cam_left_wrist.mp4` | H.264 MP4 | 左腕 RGB 视频 |
| `cam_right_wrist.mp4` | H.264 MP4 | 右腕 RGB 视频 |
| `cam_top_depth_colormap.mp4` | H.264 MP4 | 头部深度预览视频 |
| `cam_top_depth/*.png` | uint16 PNG | 深度帧序列 |
| `manifest.json` | JSON | 文件索引、时长、帧数、帧率、sync_error 统计 |
| `metadata.json` | JSON | 对齐策略、同步误差、设备信息、硬件规格（left_dof/right_dof） |
| `camera_info.json` | JSON | 三路相机 RGB/Depth 内参 + IMU 标定参数 |

- **相机**：Orbbec Gemini 335L（头部）+ Gemini 2×2（左右腕部），RGB 640×480，Depth 640×400
- **遥操作**：Linker TA（手臂）+ Linker TG/FFG/MCG（手套）

### 2.6 当前业务逻辑主路径

```
采集数据(TeleDex) → MinIO对象存储 → 扫描入库(v3) →

```

主路径中**标注是唯一缺失的环节**。

## 三、用户已确定的初步思路

### 3.1 标注放在质检之后，与质检解耦

- **已确认**：标注作为质检后的独立环节
- **标注对象**：只能是**质检通过的 episodes**（即 QcTask 判定结果为合格/可用的数据）
- **用户流程**：完成质检后，进入独立的标注界面。质检和标注不在同一页面混用。
- **待定**：入口形式 — 质检页面加"去标注"按钮？导航栏新增"标注管理"菜单？或两者结合？

### 3.2 标注方法：VLM 自动 + 人工检查为主

**主路径（80% 场景）**：
```
VLM自动生成标注 → 人工检查/修改 → 确认提交
```

**辅助路径（20% 场景）**：
```
人工全手工标注（从头逐帧标注，不依赖 VLM）
```

### 3.3 task_description 的利用

平台在创建任务类型（`TaskType`）时已要求填写 `task_description`（任务描述，如"切黄瓜"）。后续可规范化：

- 创建任务时就写好规范的 task_description
- 标注时**基于基准描述生成多种英文变体**（如 "cut the cucumber"、"slice the cucumber into pieces"），用于训练数据增强

## 四、核心待澄清问题

### 问题 1：标注内容 — 到底标注什么？

这是最核心的问题。基于机器人操作数据集的常见规范（LeRobot v3.1、Open X-Embodiment、DROID 等），候选标注项有：

| # | 标注项 | 说明 | 对应的训练用途 |
|---|--------|------|---------------|
| 1 | **语言指令** (Language Instruction) | 对整段演示的自然语言描述，如 "pick up the red apple from the table" | 训练语言条件策略（如 RT-2、Octo） |
| 2 | **子任务切分** (Action Segment / Subtask) | 将长序列切分为子动作，标注起止帧和标签，如 `[0s-3s] reach → [3s-6s] grasp → [6s-9s] lift → [9s-12s] place` | 长程任务分解、层级策略训练 |
| 3 | **物体交互标注** (Object Interaction) | 每帧/每段交互的物体、接触状态 | 物体感知策略、affordance 学习 |
| 4 | **关键帧** (Keyframes) | 任务中关键状态转换帧（如刚接触到物体、物体被提起） | 关键帧驱动策略、动作草图 |
| 5 | **结果评价** (Success/Failure) | 子任务级别是否成功 | — （QC 已有 L4 覆盖，可能重复） |
| 6 | **SAM2 分割掩码** (Segmentation Mask) | 帧级物体掩码 | 视觉 grounding、抓取点检测 |
| 7 | **task_description 英文变体** | 基于创建任务时填写的中文/英文描述，生成多个英文表达变体 | 数据增强，提高语言泛化性 |

**需要 AI 分析**：
- V1 应该优先做哪些标注项？建议的优先级排序？
- 每个标注项的数据模型（字段、存储格式、与现有模型的关联）？
- 是否直接对标 LeRobot v3.1 的 `language_persistent`（episode 级描述）和 `language_events`（帧级子任务标签）字段？

### 问题 2：标注的粒度 — 以什么为单位？

**候选粒度**：

| 粒度 | 举例 | 适用标注项 |
|------|------|-----------|
| **Episode 级** | 整段演示一条语言描述 | 语言指令 |
| **帧级** (per-frame) | 每帧一个标签 | 子任务索引、关键帧标记 |
| **时间段级** (segment-level) | 起止帧 + 标签 | 子任务切分、物体交互段 |

**需要 AI 分析**：
- 不同标注项应该用什么粒度？
- 标注结果如何存储？是在 PostgreSQL 建表（如 `annotation_labels`），还是写入文件随数据导出（如 LeRobot 的 `meta/subtasks.parquet`）？

### 问题 3：标注流程 — 状态机与权限

**已确认的约束**：
- 标注对象 = 质检通过的 episodes
- VLM 自动标注 → 人工检查为主
- 人工全手工标注为辅

**需要 AI 分析**：
- 标注任务的完整状态机？例如：`pending_auto → auto_done → awaiting_review → reviewing → approved / rejected → finalized`
- 角色设计：是否需要"标注员"角色？标注员和质检员能否是同一群人？
- 标注审核流程：是否需要多级审核（标注员 → 审核员）？还是标注员自己检查后直接提交？
- 标注进度管理：是否类似任务池（task pool）的派发/认领机制？

### 问题 4：VLM 自动标注的技术方案

**已有资源**：
- 本地 Ollama 服务已部署（Qwen3-VL-32B-Thinking）
- 后端已有 `ai_qc/` 模块（LLM client、prompt builder、SSE stream）

- 输出格式：JSON 结构化的标注结果，含置信度/替代方案？
- 失败处理：VLM 超时/质量差时，是 fallback 到人工全手工标注，还是重试？

### 问题 5：数据模型 — 需要新增哪些表和字段？

**现有相关模型**（简化）：
- `TaskType`：任务类型，含 `task_description`（文本描述）
- `Lists`：数据批次（对应 MinIO 目录）

- `QcTask`：质检任务，状态机（assigned / in_review / done）

**需要 AI 分析**：

- task_description 的"多种英文变体"如何存储？在 TaskType 表扩展字段，还是新建 `task_description_variants` 表？

### 问题 6：与现有系统的集成方式

### 问题 7：导出格式 — 标注结果如何产出？

## 五、设计约束

1. **必须与现有架构兼容**：后端 FastAPI + SQLAlchemy，前端 Vue 3 + Element Plus
2. **必须与质检解耦**：标注是独立模块，质检通过是标注的前置条件但不耦合标注状态
3. **必须支持 VLM 自动标注 + 人工检查的主路径**：不能只做人工标注
4. **必须复用已有基础设施**：Ollama（Qwen3-VL-32B）、MinIO 媒体访问协议（presigned URL）、角色权限体系
5. **标注对象固定**：只能对质检通过的 episodes 进行标注，不在标注过程中重复质检
6. **task_description 规范化**：需推动采集端/管理侧规范填写，标注时以此为基准
7. **避免过度工程**：V1 应最小可用，不要超越标注核心功能（如不做 SAM2 分割、3D 可视化等）
