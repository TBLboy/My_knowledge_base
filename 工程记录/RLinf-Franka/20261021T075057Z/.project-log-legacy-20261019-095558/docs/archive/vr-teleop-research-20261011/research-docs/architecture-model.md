# 分层架构模型（工作共识）

> **状态**：工作共识模型，由 2026-10-11 的架构讨论形成并由用户确认记录。**不是冻结的需求基线或架构决策**——冻结需走 `a-requirement-baseline` / `a-architecture-decision`。
> **依据**：本轮源码级调研（15 个仓库浅克隆）+ `第一阶段生态普查报告.md` v1.2。
> **证据分级**：沿用报告的 L0（文档声明）/ L1（元数据或网络原文）/ L2（源码可证）/ L3（外部真机）/ L4（我方实测）约定。
> **用途**：作为后续所有架构讨论的共同底图。

## 1. 一句话

**上行消除设备差异，下行消除机器人差异。** 这是整套分层唯一的动机。

## 2. 逻辑分层（修正版）

```
                ┌─────────────────────────────────────────┐
   人（操作者）  │  PICO 头显+手柄     Meta Quest 头显+手柄  │  ← 双工设备
                │  （上行：意图）      （下行：视觉反馈）    │
                └────────────────┬────────────────────────┘
                                 │  pose / buttons / tracking / timestamp
                                 ▼
                    ┌────────────────────────────┐
                    │  ① 统一 XR 输入层           │  ← 消除【设备】差异
                    │  统一格式 + 坐标系 + 时钟    │
                    └───────────────┬────────────┘
                                    ▼
                    ┌────────────────────────────┐
                    │  ② 遥操作核心层             │  ← 人的意图 → 机器人动作
                    │  坐标映射/clutch/滤波/IK/    │
                    │  限位/状态机/看门狗/安全     │
                    └───────────────┬────────────┘
                                    ▼
                    ┌────────────────────────────┐
                    │  ③ 机器人适配层             │  ← 消除【从端】差异
                    │  Franka / Piper / UR 各自 SDK│
                    └───────────────┬────────────┘
                                    ▼
                                真实机器人

        ┌───────────────────────────────────────────────────────┐
        │  ④ 数据记录层 —— 旁挂观察者（同时 tap ①②③，不是链路终点）│
        └───────────────────────────────────────────────────────┘

        ══════════ 横切关注点：时间同步（贯穿 ①②③④）══════════
```

**关键**：这是**逻辑分层**，不要求物理上分成四个进程。真实实现里常被压缩进两个进程（见 §9）。

## 3. 对早期表述的三处结构性修正

| # | 早期表述 | 修正后 | 为什么重要 |
| --- | --- | --- | --- |
| 1 | 数据记录层是"最后一层" | **旁挂观察者**，同时监听 ①②③ | 训练用的 `action` 是**③实际下发**的结果；"人当时想干什么"只有①知道。挂在末端就拿不到中间层数据 |
| 2 | 时间同步不成层，隐含 | **横切关注点**，贯穿所有层 | XR / 相机 / 机器人状态来自三个独立时钟，不对齐则回放时"手在动、画面没动"，数据作废 |
| 3 | 头显是"数据发送者" | **双工设备**（上行意图 + 下行视觉反馈） | 引出独立的产品决策：是否做下行视觉链路（盲操作 vs 远程遥操作） |

## 4. 各层职责

### ① 统一 XR 输入层

**产出物 = 统一数据契约**（Pose / Buttons / Tracking / Timestamp 四类）。

**真正的难点不是"统一格式"，而是三件事**：

1. **坐标系约定统一** —— Unity 左手系 Y-up ↔ ROS 右手系 Z-up ↔ 机器人基座坐标。最常见的坑。
2. **时间戳的对齐与单调性** —— 不同设备时钟不同源。
3. **`status`（追踪丢失）语义统一** —— PICO 丢了和 Quest 丢了，行为必须**一致**；不能一个保持最后位姿、一个跳零。

**已核实的参考数据契约**（L2，`XRoboToolkit-Teleop-ROS/ros2/xr_msgs/`）：

```
Custom.msg                     ← 一帧完整 XR 输入
  int64      timestamp_ns
  int32      input
  Head       head
  Controller left_controller
  Controller right_controller

Head.msg
  float32[7] pose              ← 3 位置 + 4 四元数
  int32      status

Controller.msg
  float32 axis_x, axis_y       ← 摇杆
  bool    axis_click
  float32 gripper              ← 握持键（模拟量）
  float32 trigger              ← 扳机
  bool    primary_button / secondary_button / menu_button
  float32[7] pose
  int32   status
```

> 本层的输出**只是"操作者想让机器人去哪"，不是"直接驱动硬件"**。安全保护不在这层。

### ② 遥操作核心层

清单（IK 只是其中一项）：

| 组件 | 解决什么 | 缺失后果 |
| --- | --- | --- |
| 坐标变换 / 映射策略 | XR 世界系 ↔ 机器人基座系；绝对位姿 vs 相对位移 | 手柄右移、机器人左走 |
| **Clutch（离合器）** | 人臂活动范围 < 机器人工作空间，需"松手→对位→继续" | 够不到的地方永远够不到 |
| 滤波 / 平滑 | XR 位姿抖动 | 机器人抖动 |
| IK 求解 | 末端位姿 → 关节角 | 无法执行 |
| 状态机 | teleop 非持续开启 | 无定义的中间态 |
| **失联看门狗** | XR 数据断流 | 机器人**保持最后指令继续运动**（极危险） |
| 限位 / 速度限制 | 关节限位、工作空间、速度上限 | 撞机 |

**滤波是真实权衡**：滤波越强越平滑，但**引入延迟越大**；延迟在遥操作里是致命体验问题 → **必须在 PoC 中量化，不能凭手感调**。

### ③ 机器人适配层

按机器人调用各自 SDK，消除从端差异。

⚠️ **本层出口的语义是本模型最大的未决问题**，见 §7。

### ④ 数据记录层

**三类"输入"必须分开存**（它们在真实系统中**绝不相等**：IK 可能失败、安全可能限幅、网络有延迟）：

| 记录项 | 是什么 | 训练时角色 |
| --- | --- | --- |
| XR 原始输入 | 手柄位姿、按键、时间戳 | 人的**意图**（回放/追溯用） |
| `action` | ③ **实际下发**的关节角/位姿目标 | 策略要学的东西 |
| `observation` | 相机图像 + 机器人**本体感受**（关节角/速度/力矩）+ **夹爪状态** | 策略的输入 |
| `metadata` | episode 编号、任务标签、相机内外参、**校准参数** | 可复现性的前提 |

> 夹爪是**独立维度**：Franka / Piper / UR 用的夹爪完全不同。
> 缺 `metadata` 中的校准参数 → 数据无法复现。

## 5. 安全是三层，不能只靠遥操作核心

| 层 | 安全职责 |
| --- | --- |
| ② 遥操作核心 | 软限位、速度/加速度限制、工作空间限制、失联停机 |
| ③ 机器人适配层 | 机器人**自身**的伺服级保护（如 Franka 力矩限制、UR 安全平面） |
| 硬件 | **物理急停**（任何软件都不得绕过） |

> 依据：`具身智能VR遥操作数据采集调研任务背景说明.md` §5 原则 3——"VR 输入是操作者意图，而不是绕开保护直接驱动硬件"。

## 6. 校准（Calibration）——必须显式建模的独立环节

XR 世界坐标系 ↔ 机器人基座坐标系的对齐，**每次开机都要做，且必须可复现、可验证**。

建议建模成**独立步骤/子状态**，不要散落在代码里。

**真实先例**：
- `Quest2ROS/quest2ros`：A+B / X+Y 按键手动对齐坐标帧
- `swaaniida/pico-piper-teleop`：独立 `preflight.py` + `config/`
- `Labelbox/lbx-Franka-Teach`：`vr_calibration_tool.py` + `vr_calibration_data.json`
- `wengmister/franka-vr-teleop`：README 明确警告"VR world frame 有原点，跨原点会导致**坐标镜像**，需按住 meta 菜单重置"

## 7. ⚠️ 本模型的未决 C 级问题（**已决定：保留待确认**）

> **状态（2026-10-11，用户决定）**：Q1–Q4 均属**具体实现问题**。用户明确决定**先行保留**，待其进一步确认后再讨论。**当前阶段不解决、不预设、不默认。**
> **纪律**：任何后续实现或文档**不得**把本节任一问题当作已决；引用时必须标注"待确认"。
> **记录**：4 个问题已登记为 `open-question` 记录 **`OQ-001` ~ `OQ-004`**（状态 `deferred`）；保留决定登记为 `decision` 记录 **`DEC-001`**（状态 `active`）。用户确认后可将其更新为 `answered`。

| # | 问题 | 两种方案 | 影响 |
| --- | --- | --- | --- |
| **Q1** | **适配层出口是"关节角"还是"末端位姿"？** | A：核心层统一 IK → 下发关节角<br>B：下发末端位姿 → 各机器人自做 IK | 直接决定"多机械臂兼容"难度。Franka **7 轴** / Piper **6 轴** / UR **6 轴**，自由度不同 → 方案 A 必须处理变自由度；方案 B 适配层薄但解算质量与安全性不可控 |
| **Q2** | 是否做**下行视觉反馈**链路？ | 不做：操作者在旁可视（简单）<br>做：远程遥操作（需带宽/延迟设计） | 产品范围决策 |
| **Q3** | 输入模态：**手柄 6DoF** 还是**裸手追踪**？ | 两者数据形态不同（pose+按键 vs 关节/关键点） | 影响①的数据契约与②的 IK |
| **Q4** | Clutch 采用哪种交互？（按键 / 手势 / 脚踩） | 各项目做法不同 | 影响可用性与安全 |

**现实证据（Q1 三种做法都真实存在，故不能默认）**：
- `XRoboToolkit-Teleop-ROS` → 方案 A（Placo/Eigen 算 IK 后发关节）
- `ZorAttC/franka_vr` → 方案 B（发位姿给 MoveIt Servo）
- `wengmister/franka-vr-teleop` → 方案 A 变体（自算 IK → libfranka **关节速度**接口）

## 8. 三个频率，永不混用

| 频率 | 含义 | 本轮实测事实 |
| --- | --- | --- |
| **XR 输入频率** | 头显推人手姿态的速率 | `franka-vr-teleop`：Quest 3S 走 USB/adb ≈ **65Hz**；WiFi UDP ≈ **20Hz** |
| **机器人控制频率** | 下发关节指令的环频 | 同项目 `CONTROL_CYCLE_TIME = 0.001` → **1kHz**；`lbx-Franka-Teach` 仅 **6.6Hz** |
| **数据录制频率** | 落盘采样率 | `lbx-Franka-Teach` ≈ **40Hz** |

看到"1kHz"就当 VR 输入是 1kHz、看到"40Hz 录制"就当机器人状态是 40Hz，都是**常见误读**。

## 9. 真实链路验证（说明分层是逻辑的，不是物理的）

`wengmister/franka-vr-teleop` 的实际实现（L2，源码）：

```
Quest 手追 App ──UDP:9000/8888──> ROS2 节点（坐标变换 + 平滑）
                                        │ UDP
                                        ▼
                        VR Robot Client（1kHz 实时环）
                          · Weighted IK (GeoFIK)
                          · Ruckig 限 jerk 轨迹
                          · 关节速度控制
                                        │ libfranka
                                        ▼
                                   Franka 机器人
```

§2 的四层在这里**真实存在**，只是被压缩进两个进程。

## 10. 术语对齐

- 本模型称"**统一 XR 输入层**"，报告与任务背景说明称"**Unified VR Input Interface**"——**同一个东西**。
- 但"XR 层"**不等于 OpenXR**：OpenXR 是**设备侧标准**（PICO / Quest 各自实现），本模型要建的是**应用侧统一抽象层**。PICO 与 Quest 都遵循 OpenXR，但**拿到的数据格式仍然不同**——这正是本层存在的理由。
