# 组合式技术路线方法论（工作共识）

> **状态**：工作共识，由 2026-10-11 讨论形成。**不是冻结的架构决策**。
> **依据**：`第一阶段生态普查报告.md` v1.2（15 仓库源码级证据）+ `architecture-model.md`。
> **用途**：指导第二阶段（候选源码分析）与 PoC 的实际工作方式。

---

## 1. 一句话

**不选"一个项目"，而是按层组合；组合的合法性来自"接口契约"，不来自"哪个项目更流行"。**

---

## 2. 为什么不能"整项目选型"

生态普查的结论是：**没有任何单一开源项目同时满足**「PICO + Quest 双端 × Franka 优先 × 多机械臂 × 数采闭环」。

但也不是从零开始——**零件已经造好了**。已有真实成功先例（L2 源码证据）：

```
lerobot_ur_dual_vrteleop = XRoboToolkit(输入层) + LeRobot(数据层) + UR5e(从端)
                           它自己只写了胶水
```

**所以"组合"是已验证的可行路径，不是纸面推演。**

---

## 3. 分层与四个接口契约

```
硬件(头显) ──[契约A: 设备 SDK / OpenXR]──> ① XR 输入层
①         ──[契约B: 统一 XR 数据]────────> ② tele 核心层
②         ──[契约C: 关节角 or 末端位姿 ★]──> ③ 输出适配层
③         ──[契约D: 厂商 SDK]────────────> 从端设备 / 仿真
                                           数据记录层 ── 旁挂 tap ①②③
```

| 契约 | 内容 | 现状 |
| --- | --- | --- |
| **A** | 设备 SDK（PICO / Quest，均实现 OpenXR 但数据格式不同） | 由 ① 兜住 |
| **B** | Pose / Buttons / Tracking / Timestamp（已有可参考的 message schema） | 3 个候选 |
| **C** | **关节角 还是 末端位姿** | ⚠️ **= `OQ-001`（Q1），未决** |
| **D** | libfranka / `piper_sdk` / ur_rtde | 各厂商文档 |

> **契约 C 就是 `OQ-001`**。因此「组合式方案」与「Q1」是**同一议题的两面**，必须一起推进；否则组合没有合法性判据，只能靠试错。

---

## 4. 🔑 关键纠正：② 应该**最先**动手，而不是最后

普查发现一个与直觉相反的事实：

| 层 | 有独立开源实现吗 | 候选数 |
| --- | --- | --- |
| ① XR 输入层 | ✅ 有 | 3~4 |
| ③ 输出适配层 | ✅ 有 | Franka 6 / UR 2 / Piper 3 |
| **② tele 核心层** | ❌ **没有整体实现**（≈0） | — |

**原因**：没有项目把"遥操作核心"单独发布，它**总被内嵌**在①或③里，且**切面位置各家不同**：

| 项目 | "核心"被切在哪 |
| --- | --- |
| `franka-vr-teleop` | IK + Ruckig 在 `robot_client/`（与从端编译在一起） |
| `xr_teleoperate` | `hand_retargeting.py` 在**输入侧** |
| `IsaacTeleop` | retargeting 框架在**设备侧** |
| `ZorAttC/franka_vr` | 外包给 `MoveIt Servo` |

**这正是"按层检索再拼接"最容易翻车的地方**——你以为对上了，其实两边切面不在同一位置。

**好消息**：核心层没有整体实现，但**子组件已成商品**：

| 子组件 | 成熟库 | 出现于 |
| --- | --- | --- |
| IK 求解 | Placo / Pink+Pinocchio / GeoFIK / MoveIt Servo | XRoboToolkit / DexTeleGym / franka-vr-teleop / franka_vr |
| 轨迹生成 | Ruckig（限 jerk） | franka-vr-teleop |
| 手部重定向 | dex-retargeting | DexTeleGym、IsaacTeleop |
| 滤波 | 自写 | xr_teleoperate (`weighted_moving_filter.py`) |

**结论**：**①挑一个、③挑一个、②自研**（站在成熟子组件上）。
**推论**：② 是自研的，**所以 ② 的接口决定了 ① 和 ③ 能否接上** → ② 必须先动手。

## 5. 复用强度：每格必须标注，不能只标"用不用"

硬约束来源：普查发现 **7 个高相关仓库无许可证或仅有免责声明**。

| 强度 | 含义 | 条件 | 本轮已知例子 |
| --- | --- | --- | --- |
| **direct-use** | 直接依赖 | 许可证必须清晰 | LeRobot（Apache-2.0）、`NVIDIA/IsaacTeleop`（Apache-2.0）、`xr_teleoperate`（Apache-2.0） |
| **wrapper-adapter** | 包一层自研接口 | 许可证必须清晰 | 给 `XRoboToolkit` 的 `XrClient` 包壳 |
| **reference-only** | **读它，然后自己写** | 无许可证的只能这样 | `lbx-Franka-Teach`（MCAP 数采思路）、`lerobot_franka_teleop`、`DexTeleGym` |
| **custom** | 完全自研 | — | ② 的 clutch / 状态机 / 看门狗 / 坐标映射 |

**无许可证的项目不能进入交付物**——只能作 `reference-only`。

## 6. 执行顺序（4 步）

| 顺序 | 做什么 | 为什么 |
| --- | --- | --- |
| **1** | 定契约 **A/B/C/D**（C 与 `OQ-001` 合并推进） | 契约是组合的合法性判据 |
| **2** | 只填**一行**垂直切片：① 选一个 + ③ 选一个 + ② 自研最小版 | **契约只有被穿过一次才知道对不对** |
| **3** | 穿通后，再横向扩 ① / ③ 候选池 | 此时才真正知道"兼容"的含义 |
| **4** | 每格标注复用强度 + 许可证过滤 | 把"组合"从幻想变成工程计划 |

**反模式**：先横向铺满 3×N 候选表，再试图拼接——两个组件接口不匹配时，横向工作全部作废。

---

## 7. 架构约束：必须锁版本

**实测证据**：两个互相独立的项目（`lerobot_franka_teleop`、`lerobot_ur_dual_vrteleop`）的安装文档**都要求把 LeRobot 钉死在同一个 commit**：

```
git checkout da5d2f3e9187fa4690e6667fe8b294cae49016d6   # LeRobot 0.3.4
```

两个不同作者、不同机器人，**都必须锁同一快照** → 说明该生态上游 API 不稳定，社区都在同一快照上工作。

**含义**：组合式方案必须**锁版本并记录锁了什么**，否则无法复现。
