# 双平台两层架构业务基线

- **ID**：`dual-platform-boundary`
- **版本**：1.0（draft，待用户与 mentor 评审后转 active）
- **状态**：draft
- **目标**：将数据采集平台拆分为两层——第一层（数据来源层）作为公司对外提供的标准产品边界，第二层（控制调度层）可插拔——并固化两层之间的接口契约与业务规则。
- **关联 Task**：`dual-platform-boundary-clarification`
- **起草日期**：2026-11-02
- **证据**：用户提供的《双平台开发约束》v1.0（`.vibe/docs/双平台开发约束.md`）+ mentor 两层架构指示 + 本轮澄清中用户的逐条确认。
- **与其他基线的关系**：
  - `unified-platform-integration-boundary` v1.6：其"runtime→worker→adapter 平台架构"降为第二层①（自研后端）内部结构；该基线需升版说明新分层或被本基线部分取代（待裁决）。
  - `hdf5-recording-final-baseline` v1.0：不受本基线影响，自研后端继续按 v1.0 落盘；RLinf 作为第二层时数据写入方归 RLinf。
  - 《双平台开发约束》：整体降格为"RLinf 作为第二层实例"的对接规范，不再是平台目标架构。

## 1. 目标架构

```text
┌──────────────── 第一层：数据来源层（公司对外产品边界）────────────────┐
│                                                                       │
│  ┌─ 硬件端点层 ──────────────────────────────────────────────────┐   │
│  │  XR 端点：Pico（现有），后续 Meta、SpaceMouse                    │   │
│  │  相机端点：三路（现有 UVC/ZED 体系）                              │   │
│  │  音频端点：预留                                                    │   │
│  └──────────────┬────────────────────────────────────────────┘   │
│                 │ 泛用格式（设备原始信号 / 相机原始帧）                 │
│  ┌──────────────▼────────────────────────────────────────────┐   │
│  │  中间层（防腐层，仍属第一层）                                      │   │
│  │  · 输入统一化：设备信号 → 统一语义事件（阈值/去抖/长按判定在此）      │   │
│  │  · 视频格式转换：原始帧 → 第二层要求的格式（如 JPEG）                │   │
│  │  · 同步流服务：相机帧组对齐（FrameSynchronizer 能力）               │   │
│  └──────────────┬────────────────────────────────────────────┘   │
│                                                                       │
│  Web 操作台（统一驾驶舱：设备管理 + 操作命令转发 + 第二层状态展示）       │
└─────────────────┼────────────────────────────────────────────────────┘
                  │ 接口 A：语义事件流 + 视频流（原始流/同步流）
                  │ 接口 B：操作命令（Web 操作台 → 第二层）
                  │ 接口 C：状态回传（第二层 → Web 展示）
                  ▼
┌──────────── 第二层：控制调度层（可插拔）────────────────────────┐
│  ① 自研后端：teleop 控制 + 采集/录制 + 上传（现有链路，同等待遇接入）   │
│  ② RLinf：控制 + 接管 + DAgger + 自带录制                           │
│  ③ 第三方后端                                                        │
└─────────────────────────────────────────────────────────────────────┘
```

拆分动机：解耦。第一层是公司对外提供的标准数据来源产品；后端可适配不同第二层（自研 / RLinf / 其他公司）。

## 3. 接口契约边界（字段级细节属后续技术设计）

- **接口 A（发布流）**：第一层 → 第二层。内容 = 统一语义事件流（XR 侧）+ 连续控制双订阅面（E1：设备信号流 + 派生目标流，含每臂 operator_engaged 标志 E2）+ 视频流（原始流或同步流，格式按第二层要求转换）。传输走 ZMQ。协议带版本；语义事件集与设备信号/目标流 schema 版本化。字段级 schema 属后续任务。
- **接口 B（操作命令）**：Web 操作台 → 第二层，请求-应答。命令集由第一层定死（A8）；初始清单见 C1（含控制权切换 C5）；参考 RLinf `OperatorBridge` 的 JSON 行协议 + `id`/`queued`/`applied`/`rejected` 回执语义作为设计输入。传输形态（Unix socket/ZMQ REQ-REP）属技术设计。
- **接口 C（状态回传）**：第二层 → Web 展示。状态集由第一层定死（A8），初始清单见 C2（按臂建模 D1，含任务统计扩展类 D2）。除运行状态和 EEF 实时状态外，第二层在连接/启动阶段发布 `robot_frame_descriptor`，声明机器人 base/EEF/TCP 坐标语义及 `operator_frame` 到 `robot_base` 的映射；每帧 EEF 状态引用 `frame_descriptor_version`，描述变化时递增版本并使旧目标失效。状态字段变更需版本化。预览类旁路信息不得阻塞第二层控制循环。
- **操作意图目录（设计原则，C3）**：B 命令集与 A 流的离散语义事件从同一份操作意图目录生成，保证 VR 入口与 Web 入口语义一致。SpaceMouse 等新设备的按键同样映射进该目录（E3），目录对设备数量开放、对语义集合封闭（版本化）。
