# 数据采集链路业务待澄清清单

- 日期：2026-10-30
- 关联 Task：`data-collection-business-clarification`
- 依据：《自采数据 HDF5 落盘规范》、active `hdf5-recording-format` v1.1、统一平台边界、架构讨论稿及现行代码。
- 目的：汇总原文未描述、描述有歧义，或统一多构型后新出现的业务问题；不重新打开已经批准的零值、EEF action、单双臂、废弃编号、原子落盘等规则。

> **2026-11-01 重审**：下列条目不是都需要用户回答。此前把技术设计和可沿用现状的事项过度推给用户澄清。action 层级、时间匹配、录制事件幂等、故障隔离、配置冻结、Schema、历史版本和保留策略应优先依据 active 基线、现行行为及安全默认由工程设计收口；只有支持松开 Grip 后的 action 缺失语义，或改变既有数据质量验收规则时，才需要用户作产品/数据决策。

## 一、本轮已经补充确认，不再作为未决项

1. **主时间轴的产生方式**：继续由实际相机同步帧组驱动；每组相机帧对齐一行机器人实测状态和 action，不按标称 fps 伪造时间点。
2. **60Hz 可配置**：后续可以以 60Hz 采集，但必需相机必须真实、同步地提供 60fps，机器人状态和 action 频率也要覆盖；禁止通过复制、插值或伪造 timestamp 把低帧率数据扩成 60Hz。

## 二、用户明确要求暂时保留的问题

### D1. 非保持状态下的 Action 间歇缺失及 episode 边界

普通松 Grip 已在 v1.2 解决：adapter 仍实际保持上一已发送目标时，action 持续有效，不再属于未决缺失。以下真正没有活动控制参考的边界仍待定义：

- 开始录制后、第一次有效 action 之前的帧如何处理；
- 真正 hold、暂停、控制权丢失及恢复期间如何处理；
- 双臂只有一侧有 action 时如何处理；
- 录制结束前最后一段没有 action 时如何处理；
- `collect_mode=teleop` 但整条 episode 没有 action 时，格式允许 observation-only 是否也意味着业务上可作为正常数据上传。

这些异常分支暂缓，不影响普通松 Grip 持续保持目标的正常采集设计。

### D2. 不完整候选帧的处理

原规范规定缺失数据不伪造、各 dataset 行数与 `timestamp` 一致，但没有明确采集端遇到以下情况时如何处理：

- 必需相机缺少一路或同步帧组不完整；
- 相机正常，但机器人实测状态缺失、超时或只有一侧有效；
- 图像、状态或其他必需信号不能组成完整行时，是整帧跳过、保留部分数据，还是直接异常结束 episode。

**当前决定**：暂时保留，不将“整帧跳过”提前固化为业务规则。帧如何处理与 episode 是否告警、拒收、人工质检是两个独立决策。

## 三、实施前优先澄清的业务问题

### P0-1. 跨构型 action 到底取哪一层控制参考

当前基线同时要求“EEF action”和“实际提交给驱动的控制参考”，但不同机器人驱动接口不同：

- 公共 runtime 输出的请求目标 `TeleopTarget`；
- adapter 经过限位、坐标变换后的 EEF 控制参考；
- 对关节型驱动经过 IK 后实际下发的关节参考。

需要明确统一 action 固定记录哪一层；对实际接收关节目标的构型，如何仍然输出统一 EEF action；是否还要额外保存公共请求目标。不能把实测状态反向当成 action。

同时需要统一 `human / command / reset / policy / leader` 等来源语义，明确复位、自动保持、故障恢复产生的目标是否属于训练 action。

### P0-2. 相机帧与状态/action 的匹配规则

原文只有一条主时间轴，没有定义：

- 从机器人高频历史样本中取“最近一帧”“最近的不晚于相机时刻的样本”还是其他样本；
- 各信号允许的最大时间差；超过阈值算无效还是告警；
- 是否允许使用相机时刻之后到达的样本；
- 双臂各自样本如何匹配同一相机时刻；
- action 的签发时刻与相机帧时刻允许相差多少，旧 action 是否仍可记录；
- 主机 `CLOCK_REALTIME` 被校时、回拨或跳变时如何保证严格递增并标记异常。

### P0-3. 录制开始、结束与控制状态的边界

需要明确：

- 开始录制是否要求相机、机器人状态、action 或遥操作已经就绪；
- 未启动遥操作时能否只采图像/状态；
- 标定、复位、暂停、故障恢复期间是否允许继续录制；
- 开始/结束按键与第一帧、最后一帧的精确边界；
- 重复开始、重复结束、保存/废弃重复事件及进程重启后的处理；
- 录制中切换机型、臂别、相机集合或采集配置是否禁止。

### P0-4. Episode 的“任务成功”和“数据质量”是否分离

原规范中的 `success` 只写“是否成功”，当前基线将正常保存记为 `success=true`，但还没有完整区分：

- 操作员认为任务执行成功；
- 文件结构自检通过；
- 数据完整、同步和质量可接受；
- 用户主动保存或废弃。

需要明确掉帧、状态超时、action 异常、频率告警分别对应正常带 warning、异常待人工质检，还是自动拒收；以及 `success/discarded` 与质检状态如何组合，避免一个字段同时承担多种含义。

### P0-5. 采集故障不能阻塞控制时的操作员语义

统一架构已确认采集是旁挂链路，不能成为运动控制关键路径，但未定义：

- 磁盘满、写入慢、编码失败、HDF5 导出失败时，遥操作如何继续或提示；
- 当前 episode 何时标记异常，哪些原始文件保留；
- 故障恢复后是续写当前 episode，还是禁止续写并新建 episode；
- 操作员是否必须停止任务、确认废弃或重新质检。

## 四、最终交付前需要澄清的业务问题

### P1-1. 质检拒收与 batch `_SUCCESS`

- 被拒绝、废弃、异常待质检的 episode 分别是否允许上传；
- 拒收条目是否保留在 manifest；
- 存在拒收或待质检条目时 batch 能否写 `_SUCCESS`；
- 人工质检通过/拒收后如何更新 attrs、manifest 和上传状态，是否允许重复审核。

现有基线只明确废弃保留文件和编号、异常需人工确认、自检失败不能绕过，以及无 `_SUCCESS` 不算完整交付。

### P1-2. 30/60Hz 等采集配置的变更边界

60Hz 的能力已确认，但仍需明确：

- 帧率在一个 episode 内是否固定；
- 同一 batch 能否混用 30/60Hz；
- 修改帧率、分辨率或相机集合是否必须新建 batch；
- 实测帧率与帧间隔告警阈值如何随配置计算。

### P1-3. 相机内外参

用户已提出采集时记录内外参，原规范只写“有标定就写”，仍需确认：

- 参数来自相机 SDK、标定文件还是人工配置；
- 外参的参考坐标系和变换方向；
- 参数与分辨率、图像流及相机序列号如何绑定；
- 未标定或读取失败时能否采集，如何标记；
- 标定变化是否允许出现在同一 batch，上传是否需额外标定文件。

### P1-4. 音频与 language 的当前范围

- 新目标是否继续采集音频；
- `language/audio_pcm`、指令图像分别从哪里产生；
- 音频独立采样如何与主时间轴关联；
- 无语言数据时整个节点省略已明确，但有音频无文本或有文本无音频时如何表达。

### P1-5. 历史数据与多版本读取

已确认不自动迁移历史 HDF5，但仍需明确：

- 新旧格式能否存在于同一 batch；
- 上传和质检按哪个版本选择验证器；
- 下游是否必须同时读取旧 schema 与新 schema；
- 旧数据是否允许继续上传，以及重复数据查重范围。

### P1-6. 原始中间文件与本地保留

已明确上传成功后保留本地数据，但尚未明确：

- MP4、NPZ、音频、信号有效性文件是否属于正式交付物；
- 仅上传 HDF5/manifest 还是同时上传原始文件；
- 本地保留期限、清理权限和磁盘不足时的处理；
- 重新导出是否允许覆盖已有 HDF5，如何保证 MD5 和 manifest 一致。

## 五、主要是技术 Schema 冻结，不必全部展开成业务讨论

以下事项仍需在技术设计中冻结，但不应与上述业务语义混为一谈：

- 最终 `spec_version` 字符串及版本升级规则；
- `observation/state` 各构型最终字段、路径、shape、dtype、单位和可选项；
- `base_extrinsics` 的挂载路径；
- `project` 是否同时写入 episode 根 attrs；
- 当前实际支持的 `collect_mode` 枚举；
- action attrs 的来源枚举及坐标系/TCP/TCP offset 的标准表达；
- 相机节点、`sensors` JSON 和 warnings 的机器可读结构。

## 六、建议后续讨论顺序

1. 先明确跨构型 action 层级和录制边界；
2. 再明确相机与状态/action 的匹配及不完整帧规则；
3. 然后分离任务成功、保存/废弃和数据质检；
4. 最后冻结 batch 封口、配置变更、标定、音频、历史兼容与保留策略；
5. 普通松 Grip 的持续 action 已在 v1.2 固化；仅真正 hold、暂停、失控等非保持状态下的间歇缺失保留，后续集中收口。
