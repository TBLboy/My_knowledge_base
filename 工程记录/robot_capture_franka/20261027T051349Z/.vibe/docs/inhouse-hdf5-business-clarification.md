## 已明确的目标与边界

- 目标交付格式为 inhouse-hdf5-v1，统一不同本体的字段结构；Franka 单臂状态使用 main，保留全部 7 个关节。
- 根 timestamp 为 float64 Unix 秒主时间轴；状态、图像逐行对应。禁止为掩盖缺失伪造时间戳或数值。
- 掉帧澄清（用户确认，2026-10-21）：主时间轴与相机图像内容分开处理。不为弥补某路相机缺帧而新增或删除主时间轴时间点；对已有时间点缺失的相机图像，优先复制同一路相机上一帧，并将对应 `<cam>_dup` 标为 true。正常帧标 false，各相机图像及 dup 数组长度均与主时间轴 T 一致。此规则不授权复制或伪造机器人状态。首帧无可复制图像、连续缺失等情况下何时必须拒收整条 episode 尚待明确。
- 图像使用逐帧 JPEG、vlen uint8；字段必须标注相应单位、维度与坐标约定。没有采集的数据不写，不写全零占位。
- 观测与控制目标严格区分，不能把 TCP 目标改名为关节动作，也不能把目标写成实测 eef_pose。
- 开批前从任务模板选择 task_id 和 task；同一批次只含一个任务，换任务开新批次。具体模板来源和交互尚未确定。
- 交付目录、批次日期和编号、文件名遵循原文；本地缓存目录不必直接等同于 OBS 交付目录。
- 原文要求人工废弃条目保留、标注 discarded/discard_reason 并上传。这与现有 X/网页丢弃直接删除的已实现行为冲突；迁移行为及拒收例外尚待确认，当前不修改或删除历史数据。
- 人工废弃交互澄清（用户确认）：录制中第一次按 X，弹出悬浮的废弃原因输入框，预填“操作失误”，不立即停止或废弃。弹窗期间继续录制；取消只关闭弹窗并继续采集。用户可以编辑原因，再次按 X 或点击“确定”执行一次废弃；未修改时使用默认原因。再次按 X 必须先松开再重新按下，长按不得触发确认。确认后停止录制、保留当前轨迹，写 discarded=true 和实际确认的 discard_reason，随后自动复位；条目按规范进入批次清单及上传流程。网页“丢弃本次采集”复用同一交互。录制中 A+X 也打开同一确认弹窗，确认后废弃并复位；未录制时 A+X 仍直接复位。此为已批准的待实现行为，替换原先直接删除文件的人工废弃语义；不代表格式损坏条目获准上传。
- 目标交付包含上传前自检、manifest、MD5 和最后写入的 _SUCCESS；封口后不再追加。第 11 项帧率检查是告警，其余按规范拒收规则落实。
- 第 6 节 JPEG→H.264 属于数据侧，不属于此次采集侧改造。
- 历史数据只迁移可可靠恢复的信息，不伪造操作员、场景、成功状态、真实动作或已删除轨迹。

## 相机首帧就绪澄清（用户确认）

- 正式开始录制前，检查所有必需相机均有新鲜、有效图像，全部就绪才开始轨迹。
- 任一路未就绪，拒绝本次开始，在网页提示具体相机；不创建轨迹、不占 episode 编号。
- 若这是待采集批次的第一条轨迹，检查失败不构成正式开始，不分配正式 batch_id。
- 开始后缺帧，按已确认规则复制同一路相机上一帧并标 `<cam>_dup=true`，不增删主时间轴时间点。
- 新鲜度的具体技术阈值及连续缺失、机器人状态缺失的异常边界尚未由本条定义。

## 录制中相机持续掉线澄清（用户确认）

- 不增加“相机持续掉线达到超时就自动停止录制”的采集期规则，避免误触发和过重的采集期防护；撤回此前自动停止的建议。
- 开始录制后的相机缺失仍沿用上一帧复制及 `<cam>_dup=true` 标记规则，不为此增删主时间轴，保留异常信息供质检识别。
- 持续缺帧规则（用户进一步确认）：一直缺帧就一直复制同一路相机最后一张有效图像，每个复制位置均标 `<cam>_dup=true`，直到恢复有效图像或本条录制结束；不设置连续复制时长或复制比例上限，不据此自动停止录制或自动拒收。首帧前置就绪检查仍保留。
- 不再将“连续复制多久或复制占比多少必须拒收”列为待确认事项。不新增该阈值型质检规则；规范中其他既定自检仍执行，不能将本条理解为豁免其他检查。
- “筛掉”指质检拒收，不授权物理删除、重新编号，或跳过拒收轨迹后直接封口；这些仍受待定的拒收批次处理规则约束。
- 开始前的相机首帧就绪检查保持不变；本条不放宽机器人控制安全保护，也不决定机器人状态缺失处理。

## 零值与缺失字段澄清（用户确认）

- 本规则的业务含义是禁止伪造全零占位，不是禁止真实数据为零。
- 实际采集得到的零值必须如实保留，包括部分时段、某一维度及整个数值 dataset 全零；不得仅因全零而拒收、删除字段或修改真实数值。
- 没有采集或字段缺失时，省略对应字段，禁止补零冒充真实测量或真实动作。
- 自检应核实字段是否来自实际采集，不能仅凭数值全零推断缺失或伪造。
- 撤回此前“任意维度整列全零即拒收”和“整个 dataset 全零即拒收”的解释。用户已明确业务口径，不再将真实零值是否允许列为待澄清项；审批规范原文保持不变。

## 成功状态澄清（用户确认）

- Pico Y 与网页“停止并保存”共用成功结束语义：success=true、discarded=false，按既定流程保存后自动复位。
- X、录制中 A+X 或网页丢弃，经原因弹窗确认后：success=false、discarded=true，保留原因与轨迹并自动复位。
- 本次不新增“失败但不废弃”的操作入口；异常中断不得自动标为成功。异常数据的拒收和批次处理仍待澄清。
- HDF5 root attrs 与 manifest 对应 episode 的 success/discarded 保持一致。这是待实现的已确认规则，不代表现有文件已包含这些标签。

## 操作员与场景澄清（用户确认）

- 开始批次前，网页必须提供 operator（操作员）和 scene（采集场景）的输入、确认位置。
- 两项可预填上次使用的值，但必须由用户确认；去除首尾空白后不得为空，不猜测身份、不填虚假的默认值。
- 开批后固定，整个批次及其每条 episode 使用同一组值；写入 HDF5 root attrs 和批次 manifest，保持一致。
- 后续实现规划必须包含网页布局、输入校验及开批后只读展示，不能只增加后端字段。
- 建议的布局（尚属实施设计）：在采集页的批次准备区域并列放置“操作员”“场景”输入框，显示必填提示；开批时校验，批次进行中只读显示。与任务选择及批次生命周期一起设计，具体布局不提前作为已批准需求。

## 结束批次与交付封口澄清（用户确认）

### 新建批次与编号（用户确认）

- 网页提供“新建批次”按钮，选择 project、robot_id、任务，填写或确认 operator、scene；确认后进入待采集状态。任务模板来源仍按待定事项处理。
- 第一条轨迹真正开始采集时才分配正式 batch_id，日期取该时刻的北京时间；提前建批或待采集期间跨午夜不提前固定日期。
- 在同一 project/robot_id/task_id 目录内，同日批次编号从 01 开始自动递增，形成 YYYYMMDD_NN；编号持久保存，重启不重复、不覆盖已有批次。
- 一个工作台同时只采集一个批次，未结束时不能新建另一个；结束后可新建下一批，旧批上传状态独立保留。
- 尚未采集第一条轨迹时允许取消建批，不占正式批次编号，不产生空交付批次。
- 新建与结束批次均只在网页操作，不映射手柄；手柄保留轨迹级操作。

### 结束与封口

- 上传后本地保留规则（用户确认）：批次上传成功、服务器写入 _SUCCESS 后，仍保留本地批次数据，供回放、排查和备份；不得因交付成功自动删除本地数据。本条不授权新增自动清理策略。

- “结束批次”按钮仅在网页提供，不映射 Pico 手柄按键；是否结束批次由网页操作决定。
- 跨日规则（用户确认）：结束批次只能由网页手动控制，不因午夜跨日自动结束或切换批次。批次 ID 日期固定为第一条 episode 开始时的北京时间日期；跨日继续采集时批次 ID 不变，每条 episode 文件名仍使用自身实际开始时刻（北京时间）。手动结束后新开批次，其日期由新批第一条 episode 决定。异常中断后的恢复规则另行澄清，不由本条推定。
- 录制过程中不能结束批次，必须先保存或确认废弃当前轨迹。
- 用户确认结束批次后，该批次不再接收新轨迹；结束采集不等于交付完成。
- 上传触发方式（用户确认）：结束批次与上传分离。结束批次不自动上传，避免测试数据未经用户决定进入服务器；必须由用户在网页另行手动点击“上传批次”发起交付。不把此前建议的自动上传作为实施方案。
- 手动上传仍须满足既定自检、异常轨迹人工确认及清单核对要求；全部满足后才允许在服务器写 _SUCCESS。失败由网页展示原因并支持手动重试，不因结束批次或采集完成自动触发上传。
- 上传重试规则（用户确认）：上传中断或失败后，由用户在网页手动重试同一批次；不新建批次、不改变 batch_id 或 episode 编号。已上传且校验一致的文件跳过，缺失或传坏的文件重传；不能仅凭文件存在或大小相同认定校验一致。全部核对完成后才写 _SUCCESS，避免重复交付；具体远端校验方式仍在上传技术设计中落实。
- 重启续批规则（用户确认）：程序重启后恢复尚未结束批次的信息，由用户在网页确认后继续采集；沿用原批次 ID 和编号序列，保留已有编号，不覆盖旧轨迹。不自动开始录制，不自动启动机器人。已手动结束的批次不可恢复追加，即使尚未完成上传或写入 _SUCCESS；其后续只进行既定交付或重试。异常中断时未完成的单条轨迹如何处置仍属待澄清事项。
- 完成数据自检、HDF5 上传及 manifest 与服务器实际文件一一对应的核对后，最后在服务器该批次目录上传或创建独立的 `_SUCCESS` 文件。
- `_SUCCESS` 表示整个批次完成质检、上传及清单核对，并已封口；不是单条轨迹的 success 标签，不能仅在本地写标记替代服务器标记。
- 文件上传过程中服务器可以看到部分文件，但没有 `_SUCCESS` 时不能认定完整交付。不得提前发布该标记。
- 校验、上传或清单核对失败时，不写 `_SUCCESS`，网页展示原因，支持处理后重试，不宣称交付完成。
- 原文未规定 `_SUCCESS` 文件内容；是否使用空文件以及本地是否保留标记尚非已批准的业务要求。
- 批内存在格式损坏、无法上传轨迹时，如何处理该轨迹与整个批次仍待后续拒收/异常处理澄清；不得自行跳过损坏条目后封口。

## 项目与机器标识澄清（用户确认）

- project 表示数据采集项目；task_id/task 表示机器人具体执行的任务。一个项目可包含多个任务，一个批次只含一个任务；换任务开新批次，不一定换项目。
- 配置文件维护可选 project、robot_id 及关联关系。网页开批前通过下拉选项选择，不自由输入。
- robot_id 必须对应实际连接机器；当前仅一台 Franka 时自动选中并锁定其编号，项目仍可选择。
- 开批后将选定值固定到批次，按规范用于交付目录、manifest 和对应 HDF5 字段；后续配置修改不改写历史批次。
- 实际项目名、机器编号及配置文件具体布局仍需部署时提供或在实施设计中落实，不自行编造。

## 异常中断轨迹澄清（用户确认）

- 意外中断时保留正在录制轨迹的残留文件及已分配编号，不覆盖，不自动标记成功。
- 网页显示“异常中断，待检查”。
- 即使自检通过，也不直接作为成功轨迹上传；具体归类待人工确认，不根据文件完整性推断任务成功。
- 自检失败时进入待定的拒收轨迹处理事项，不擅自跳过后封口；此前“剔除拒收轨迹、其余仍可封口”的提议仍未获批。
- 人工归类交互（用户确认）：复用现有回放页面，不另建页面。仅“异常中断，待检查”的轨迹显示“确认为成功”和“确认为废弃”按钮；正常完成的轨迹不显示这两个补确认按钮。
- 用户先回放检查，再确认归类。成功时写 success=true、discarded=false；废弃时弹出原因输入框，确认后写 success=false、discarded=true 并保留原因与数据。未确认前禁止上传。
- 这是历史轨迹的数据标签确认，不发送机器人控制命令、不触发复位；不能绕过自检或把自检失败轨迹通过人工确认变成合格数据。
- 具体编号缺口处理仍待确认；本条不授权新增规范字段或改变废弃条目上传要求。

## 拒收轨迹剔除提议（待定，未批准）

- 人工废弃与质检拒收继续区分，不能用 discarded 标记绕过质检。

8. OBS 上传入口、凭据配置、MD5 校验方式及异常批次的封口边界。正常批次最后在服务器写 _SUCCESS 已确认；ETag 不默认等同于 MD5。
