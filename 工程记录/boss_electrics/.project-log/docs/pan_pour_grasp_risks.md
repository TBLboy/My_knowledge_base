# PanPour 抓锅风险点记录

## 当前设计假设

PanPour 抓锅阶段当前思路是：感知到锅把后，左臂直接一步移动到锅把抓取点，然后执行抓取。

这个设计依赖锅把处于比较端正的水平朝左姿态。如果锅把发生角度偏移，抓取成功率会下降。

## 风险 1：一步到位接近抓取点可能碰撞锅把

风险描述：

- 机械臂直接从当前位置一步移动到抓取点时，运动轨迹可能碰触锅把。
- 碰撞可能带动锅把旋转，导致最终抓取姿态失效。

当前缓解思路：

- 将“靠近”拆成两步。
- 第一步先移动到抓取点正上方。
- 第二步再垂直下降到达抓取点。
- 这样可以降低轨迹穿越锅把区域的风险。

后续实现前仍需定案：

- “抓取点正上方”具体定义在哪个坐标系，以及安全高度。
- “垂直下降”的方向是机器人基座/中心坐标系垂直轴，还是锅具局部坐标系的某一轴。
- 两步移动的速度、安全距离和超时。

2026-08-16 调查更新：

- 用户已倾向把接近高度参数放在 PanPourSkill 内，Policy 仍只下发最终法兰目标 `a`；Skill 计算 `b = a + [0, 0, h]`（左臂 base），并带同一法兰姿态。
- 当前 driver 的 `MoveCartesian` 服务是单点阻塞式执行，两个 `MOVE_CARTESIAN` 原语或一个多航点原语都仍会在 `b` 点停顿，不能满足“不停顿直接前往 `a`”。
- driver 没有暴露 append/batch 服务；`FollowCartesianTrajectory.action` 未接线。
- MotionExecutor 内现有 `LOCAL_JOINT_TRAJECTORY` / `LOCAL_DELTA_FLANGE_REPLAY` 已使用 xCore `moveAppend` 批量执行，是当前唯一现成的连续执行通道；实现连续接近大概率要复用或扩展这条本地回放链路。
- 仍待确认：`b` 点是否允许小 blend 过渡，以及参数名、默认高度和速度。

## 风险 2：上游开盖动作可能改变锅把朝向

风险描述：

- 打开锅盖是其他组的任务。
- 上游开盖结束后才进入 PanPour 抓锅任务。
- 如果开盖动作导致锅盖或锅把发生旋转，锅把不再水平朝左，PanPour 按原思路抓取的成功率会明显下降。

当前状态：

- 尚未确定解决方案。
- 后续可讨论方向包括：感知阶段增加锅把朝向校验、失败后重新规划抓取姿态、对偏转锅把做姿态补偿、增加重试或失败上报等。
- 在方案确定前，不修改现有抓锅逻辑。

## 记录说明

本文件只记录风险、思路和待定项；当前不修改产品代码。

## 2026-08-16 固定法兰姿态导致部分 IK 失败

问题：

- V1 抓锅当前使用固定 `grasp_tcp_orientation_rpy`，转换后得到固定法兰 RPY。
- 部分视觉目标位置下 IK 失败，例如位置 `[0.606205536, 0.434084815, 0.132872672]`、RPY `[2.573030983, 1.392851630, 2.696301008]`。
- 已排除标定变化和 offset 全 0 回归问题；根因是固定姿态与目标位置组合不可达。

候选方案 A（PCA 对齐模板姿态）：

- 保留固定 RPY 作为模板。
- 每个检测帧将 TCP X 轴对齐 `-normalize(PCA_C)`。
- 使用模板 X 轴到目标 X 轴的最短旋转生成动态 TCP RPY，保留手腕接近方式和绕锅把 roll。
- 继续走现有 `grasp_flange_target()` 转换和 `/robot_driver/move_cartesian` 执行链路。

几何依据：

- 当前固定 TCP 姿态 X 轴与感知 PCA 点积约 `-0.99`，说明固定姿态本身已隐含 TCP X 轴与锅把方向反向对齐。

状态：

- `candidate`，待用户补充方案后对比定案。
- 若确认，先在本地视觉测试脚本做 PCA 对齐原型，用失败点 `--dry-run` 验证 IK，再改正式 Policy 和测试。
