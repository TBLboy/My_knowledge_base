## 一、整体架构理解（我的总结）

taskplanner 节点的主要作用就是，暴露一个服务接口，外部调用开始任务。然后节点根据传入参数创建任务上下文 task context，然后内部定时器每秒触发一次，只要存在上下文，工厂就自动运行，调用 `_generate_goal_by_task_type()` 生成对应的 goal。

这里分为两个层级：

```
顶层（编排器 Orchestrator）：Node 本身
  ├─ 负责创建 context
  ├─ 定时器自动触发调度
  └─ 状态门控 + 路由分发

底层（工人 Worker）：Policy + Builder
  ├─ Policy：根据 context 产生 "初级材料" PlannedStep
  └─ Builder：根据 PlannedStep.plan_type 路由到不同 build 函数
       → 转化为 ExecuteTask.Goal（具体可执行的 goal_msg）
```

Policy 产生的 goal 本身还不具备完整的运动信息，只是一个初级材料，需要根据 `goal.plan_type` 的类型路由到不同的构建函数。

构建函数返回具体的 `goal_msg` 给到 `_on_tick()`，然后调用 `_send_execute_task_goal(goal_msg)` 来执行。这个函数会调用 Node 里面的 ActionClient 来发送 action。

之后 `_on_tick` 就会被状态机门禁阻拦停止发送动作，直到一个动作执行结束，`_on_result` 才会重新清除状态机。

**关键认识：Node 内部分成一个运行模式 + 多个 worker。** 整个流程涉及到几个 worker：policy、builder、ActionClient + 回调。

## 二、完整运行时间线（test_gripper 示例）

```
t=0     外部调用 StartTask
         ↓
         _on_start_task()
         ├─ valid_task_types 检查 ✓
         ├─ _prepare_start_task_context()
         │    ├─ _generate_task_id() → "task_001"
         │    ├─ _active_task_id = "task_001"
         │    ├─ _active_task_type = "test_gripper"
         │    └─ _initialize_policy("test_gripper")
         │         → self._policy = TestGripperPolicy(max_loop=3)
         ├─ _clear_runtime_state()
         │    ├─ policy.clear()
         │    ├─ _pending_goal = False
         │    └─ _left/right_arm_busy = False
         └─ robot_state = IDLE
         → response.accepted = True

t=0~1   （等待下一次定时器触发）

t=1     _on_tick() 触发
         ├─ 门1: _active_task_id = "task_001" → 通过
         ├─ 门2: 双臂都空闲 → 通过
         ├─ 门3: _pending_goal = False → 通过
         ├─ 门4-6: state = IDLE → 通过
         ├─ _generate_goal_by_task_type()
         │    ├─ policy.select_next_goal()
         │    │    → PlannedStep(plan_type="gripper_action",
         │    │                   action_name="张开", arm_type=1)
         │    └─ 路由到 _build_gripper_action_goal()
         │         → ExecuteTask.Goal(task_type="gripper_action",
         │                           target.action_name="张开")
         └─ _send_execute_task_goal(goal)
              ├─ _pending_goal = True
              ├─ _right_arm_busy = True
              └─ send_goal_async() → MotionExecutor

t=1~2   _on_tick 触发：
         └─ _pending_goal = True → return（跳过）

t=2~3   _on_tick 触发：
         └─ _pending_goal = True → return（跳过）

t=3.5   MotionExecutor 完成"张开右手"，返回结果
         → _on_result() → _pending_goal = False

t=4     _on_tick 触发
         ├─ 通过所有闸门
         ├─ policy.select_next_goal()
         │    → PlannedStep(action_name="扎取")
         └─ _send_execute_task_goal(...)
              → 发送"扎取右手"

... （重复 6 次，完成 3 轮）

t=20    policy.select_next_goal() → None
         → _on_tick 清理
         → _active_task_id = None
         → 任务结束
```

## 四、Planner 内部的属性分类（回到三个问题）

### Q1：这些属性是状态机吗？这种思维叫什么？

**不是严格意义上的状态机，但有状态机的成分。**

先区分两个东西：

```python
# 这是"任务上下文 / 元数据"
self._active_task_id         = "task_001"       # 当前在做什么任务
self._active_task_type       = "test_gripper"   # 当前任务类型
self._target_class           = ""               # 当前任务目标
self._policy                 = TestGripperPolicy # 当前任务的决策逻辑

# 这是状态机变量
self._world.robot_status.state  = RobotState.IDLE  # 真正的状态
```

关键区别：

| 类型          | 变量                                                                                      | 是什么                     |
| ----------- | --------------------------------------------------------------------------------------- | ----------------------- |
| **元数据/上下文** | `_active_task_id`, `_active_task_type`, `_target_class`, `_policy`                      | 记录"当前正在做什么任务"的上下文信息     |
| **状态机**     | `robot_status.state`（IDLE / PREPARING_TASK / EXECUTING_TASK / PAUSED / SUCCESS / ERROR） | 明确枚举了系统处于什么工作阶段，并需要受控切换 |

`_pending_goal` 和 `_left_arm_busy` 也不是状态机，它们是**忙标志**（busy flags），更接近"信号量/锁"的思维。

**更精确的划分：四个层面的属性协作**

```
1. 上下文层（元数据）
   _active_task_id, _active_task_type, _target_class, _policy
   → _on_start_task 设置，_on_tick 做完后清除 _active_task_id
   → 跨 tick 持久化

2. 运行状态层（真正的状态机）
   _world.robot_status.state = IDLE / PREPARING / EXECUTING / PAUSED / SUCCESS / ERROR
   → 各函数在不同时机修改，_on_tick 的门控依赖它

3. 门控标志层（锁/信号量）
   _pending_goal, _left_arm_busy, _right_arm_busy
   → _send_execute_task_goal 设置，_on_result 清除
   → 防止重复发送、控制双臂并发

4. 代际保护层（防过期回调）
   _goal_epoch
   → _on_start_task / _on_pause_task 时 +1
   → 闭包 _on_result 和 _on_goal_response 中校验
   → 防止过期回调错误地修改当前状态
```

**这种组织方式在工程上通常叫作"Orchestrator（编排器）模式"：**

> 一个中心节点持有当前工作上下文，定期检查能否继续推进，把每一步的具体决策委托给子组件（Policy），把执行委托给远程执行器（MotionExecutor）。

用你熟悉的概念类比：

```
Orchestrator = TaskPlannerNode
  持有上下文（当前任务 ID、类型、策略）
  驱动调度（定时器 _on_tick）
  委托决策（Policy）
  委托执行（Action → MotionExecutor）
```

另一个常见的类比是 **"Master-Worker"（主-工作者）模式**：

```
PlannerNode      = Master（规划调度）
MotionExecutor   = Worker（执行动作）
```

Planner 说："下一步该做什么了？"
Policy 回答："该操作右臂了，张开手。"
Planner 封装成 goal → 发送给 MotionExecutor
Planner 等待回复
回复到达后 Planner 再次问 Policy："再下一步呢？"

所以 `_active_task_id` 这类属性的核心作用就是：**让这个循环在每次 `_on_tick` 触发时，知道自己正在处理哪个任务、处于哪个阶段**，这样才不会把不同任务的状态搞混。

### Q2：每个任务有自己的状态机吗？

**有，每个 Policy 内部维护了自己的"步骤状态机"。**

`TaskPlannerNode` 有一个统一的 `_policy`，但 `_policy` 指向的具体 Policy 实例是随着 `task_type` 变化的：

```
test_gripper  → TestGripperPolicy  实例
cut_cucumber  → CutCucumberPolicy  实例
sweet_three   → SweetPolicy        实例
```

每个 Policy 内部都会追踪"已经执行到第几步了"。

以 `TestGripperPolicy` 为例：

```python
class TestGripperPolicy(BasePolicy):
    def __init__(self, max_loop=3):
        self._max_loop = max_loop
        self._cached_steps: Optional[List[PlannedStep]] = None

    def select_next_goal(self, ...):
        if self._cached_steps is None:
            self._cached_steps = self._create_steps()  # 生成 6 个步骤

        for step in self._cached_steps:
            if step.status in (PENDING, FAILED, IN_PROGRESS):
                if step.status != IN_PROGRESS:
                    step.status = IN_PROGRESS         # ← 标记"正在执行"
                return step                           # ← 返回这一步骤

        return None  # ← 所有步骤都完成了
```

Policy 内部相当于：

```
一个步骤列表 + 当前执行指针 + 每个步骤的状态
```

这是一个**轻量级的步骤状态机**。对外暴露的接口始终只有两个方法：

```python
select_next_goal(task_id, task_type, target_class)  # → 下一步
update_step_status(step_index, status, reason)       # ← 回调更新
```

### Q3：`ExecuteTask.Goal` 是什么？

**`ExecuteTask` 是一个 ROS 2 Action 定义（`ExecuteTask.action`），而 `ExecuteTask.Goal` 就是这个 Action 的 Goal 部分**。

Action 文件由三个区域组成，用 `---` 分隔：

```
# Goal ← "请求"（TaskPlanner → MotionExecutor）
string task_id
string task_type
TaskTarget target
...

---
# Result ← "响应"（MotionExecutor → TaskPlanner）
bool success
string error_msg
...

---
# Feedback ← "进度更新"（执行过程中不断返回）
string phase
float32 progress
```

ROS 2 会根据 `.action` 文件自动生成三个消息类：

```python
from dexbot_interfaces.action import ExecuteTask

ExecuteTask.Goal        # 请求消息
ExecuteTask.Result      # 反馈消息
ExecuteTask.Feedback    # 进度消息
```

整个动作的三层封装关系：

```
ExecuteTask.Goal                      ← 发给 MotionExecutor 的"任务信封"
├── task_id = "task_001"              ← 信封上的任务编号
├── task_type = "gripper_action"      ← 信封上的"业务类型"（MotionExecutor 据此选 handler）
└── target = TaskTarget               ← 信封里的具体指令
    ├── action_name = "张开"           ← 做什么
    └── arm_type = 1                  ← 哪只手做
```

到了 MotionExecutor 端：

```python
# motion_executor_node.py
async def _execute_task_cb(self, goal_handle):
    task_type = goal_handle.request.task_type.lower()   # "gripper_action"
    skill = self._skills.get(task_type)                  # 查字典 → GripperActionApi
```

这就是整个 **TaskPlanner → MotionExecutor 的通信契约**：`task_type` 是路由键，`TaskTarget` 是参数载荷。

## 五、补充：_on_tick 的完整门控链条（补充细节）

`_on_tick()` 不是简单的 if-return，而是 6 道门按顺序检查：

```python
# task_planner_node.py ~line 455
def _on_tick(self):
    # 门 0：没有 active task → 不调度
    if self._active_task_id is None:
        return

    # 门 1：双臂都忙 → 等待
    if self._left_arm_busy and self._right_arm_busy:
        return

    # 门 2：_pending_goal 阻塞（单臂兼容）
    if self._pending_goal:
        return

    # 门 3：SUCCESS 状态
    if self._world.robot_status.state == RobotState.SUCCESS:
        return

    # 门 4：PAUSED 状态
    if self._world.robot_status.state == RobotState.PAUSED:
        return

    # 门 5：不是 IDLE
    if self._world.robot_status.state != RobotState.IDLE:
        return

    # → 全部门控通过
    goal_msg = self._generate_goal_by_task_type()
    if goal_msg is None:
        # 任务完成：设 SUCCESS，清 _active_task_id
        ...
        return
    self._send_execute_task_goal(goal_msg)
```

关键理解：门 **1 和门 2 是不同的概念**：

- **门 1（双臂忙）**：双臂模式下，只有两臂都忙才阻塞。一臂空闲就可以推进（给空闲臂发下一个 goal）。
- **门 2（_pending_goal）**：单臂模式的保护。一个 action 没执行完之前不能发下一个。

## 六、补充：_send_execute_task_goal() 内部机制

这个函数做了 7 件事，顺序不能乱：

```python
# ~line 757
def _send_execute_task_goal(self, goal_msg):
    # 1. 等 ActionServer 就绪
    self._execute_client.wait_for_server(timeout_sec=1.0)

    # 2. 更新机器人状态
    self._update_robot_state(RobotState.PREPARING_TASK)

    # 3. 记录当前 goal 的任务类型和执行模式（供状态查询用）
    self._active_goal_task_type = goal_msg.task_type
    self._active_goal_execution_mode = int(getattr(goal_msg, "execution_mode", 0))

    # 4. 设置 pending 标志（阻塞后续 tick）
    self._pending_goal = True

    # 5. 传递 resume_restart 标志（MotionExecutor 处理）
    goal_msg.resume_restart = bool(self._resume_restart_requested)
    self._resume_restart_requested = False

    # 6. 设置双臂忙标志
    #   execution_mode > 0 → 双臂都忙
    #   单臂 → 根据 arm_type 设置对应臂
    if getattr(goal_msg, 'execution_mode', 0) > 0:
        self._left_arm_busy = True
        self._right_arm_busy = getattr(goal_msg, 'co_target', None) is not None
    else:
        if goal_msg.target.arm_type == 1:
            self._right_arm_busy = True
        else:
            self._left_arm_busy = True

    # 7. 使用闭包注册回调（构建时捕获 goal_epoch）
    send_future = self._execute_client.send_goal_async(
        goal_msg, feedback_callback=_on_feedback
    )
    send_future.add_done_callback(
        lambda f: self._on_goal_response(f, _on_result, self._goal_epoch)
    )
```

### 6.1 `_on_goal_response()` — Goal Handle 确认

```python
# ~line 800
def _on_goal_response(self, goal_future, _on_result, expected_epoch):
    # 重要：epoch 校验 — epoch 变了就放弃（防止暂停→恢复后的过期回调）
    if expected_epoch != self._goal_epoch:
        goal_handle.cancel_goal_async()
        return

    # 保存 goal handle（供后续 cancel_goal_async 使用）
    self._active_goal_handle = goal_handle

    # 注册真正的 result 回调
    goal_handle.get_result_async().add_done_callback(_on_result)
```

### 6.2 `_on_result()` 闭包 — 结果处理

这是定义在 `_send_execute_task_goal()` 内部的闭包函数。捕获了 `goal_epoch`、`goal_msg` 等变量。

**成功路径（单臂）：**

```python
self._pending_goal = False
self._left_arm_busy = False
self._right_arm_busy = False
self._update_robot_state(RobotState.IDLE)          # 状态回到 IDLE
self._policy.update_step_status(
    step_index=self._current_step_index,
    status=StepStatus.COMPLETED,                   # 标记完成
)
self._current_step_retry_count = 0
```

**失败 + 重试路径：**

```python
retry_count = self._current_step_retry_count
if retry_count < 3:
    self._current_step_retry_count = retry_count + 1
    self._update_robot_state(RobotState.IDLE)      # 回 IDLE 允许重试
    # 注意：这里不更新 policy 步骤状态
    # 下次 select_next_goal() 还会返回同一个 PENDING 步骤
else:
    self._update_robot_state(RobotState.ERROR)
    self._policy.update_step_status(
        step_index=self._current_step_index,
        status=StepStatus.FAILED,                   # 标记失败
        failure_reason=result.error_msg,
    )
```

**取消检测路径：**

```python
if not result.success and result.error_msg.startswith("Canceled"):

    return
```

```python
if dual is not None and self._co_step_index is not None:
```

## 七、补充：暂停/恢复机制

```python
# ~line 350
def _on_pause_task(self, request, response):
    # 1. epoch +1，使所有进行中的回调失效
    self._goal_epoch += 1

    # 2. 如果有正在执行的 goal，取消它
    if self._pending_goal and self._active_goal_handle is not None:
        self._active_goal_handle.cancel_goal_async()

    # 3. 清空运行时状态
    self._clear_runtime_state()

    # 4. 机器人状态设为 PAUSED
    self._update_robot_state(RobotState.PAUSED)

    # 注意：_active_task_id 保留！后续 resume 时要用
```

恢复时调用 `StartTask(resume=True)`：

- `_prepare_start_task_context(resume=True)` → 保留已有 `_active_task_id`，重新创建 Policy
- `_clear_runtime_state()` → 清空所有运行标志
- `robot_state = IDLE` → 门控放行
- 下次 `_on_tick` 正常推进

## 八、补充：感知场景更新

```python
# ~line 260
def _on_scene(self, msg: ScenePerception):
    if not msg.scene_valid:
        return

    self._world.objects.clear()          # 清空旧场景
    for obj in msg.objects:
        # 四元数 → RPY 转换
        roll, pitch, yaw = _quaternion_to_rpy(qx, qy, qz, qw)

        world_obj = WorldObject(
            id=obj.id,
            class_name=obj.class_name,
            x=obj.pose.position.x, y=obj.pose.position.y, z=obj.pose.position.z,

        self._world.objects[world_obj.id] = world_obj
```

`WorldState.objects` 是 `Dict[str, WorldObject]`，每次 `_on_scene` 完全重建。Policy 的 `select_next_goal()` 可以通过 `self._world.objects` 读取最新的感知结果。

skills是干什么的？

核心结论：Skill 不做轨迹规划，只做动作分解。

Policy 发给 MotionExecutor 的 ExecuteTask.Goal 里只包含"目标位姿"（grasp_pose, place_pose 等几个点位）。Skill 的 job 就是把这些离散的目标位姿拆成一个子步骤序列。

以 PickAndPlaceSkill 为例：Policy 给了 3 个位姿（grasp_pose, place_pose, check_pose），Skill 拆成 10 个 MotionPrimitive：
  MOVE_CARTESIAN → grasp_above（接近，新生成的中间位姿）
  MOVE_CARTESIAN → grasp_pose（到位，用 Policy 给的位姿）
  GRIPPER_ACTION → "扎取"（闭合手爪）
  MOVE_CARTESIAN → lift_pose（抬升，新生成的中间位姿）
  MOVE_CARTESIAN → check_pose（检查，用 Policy 给的位姿）
  MOVE_CARTESIAN → place_above（接近放置点）
  MOVE_CARTESIAN → place_pose（放置）
  GRIPPER_ACTION → "放下"（张开手爪）
  MOVE_CARTESIAN → retreat_pose（退避）
  GRIPPER_ACTION → "扎取"（安全姿态）

关键：每个 MotionPrimitive 的 trajectory 里只有 1 个 waypoint（单目标位姿），不是一条规划好的路径。Skill 只是把"抓起来放到那边"拆成"接近→到位→抓→抬升→...→放→退"的序列。

真正做轨迹插值/规划的是 RobotDriver。当 _execute_motion_primitive() 调用 RobotDriver 的服务时（/robot_driver/move_cartesian），Driver 内部完成逆运动学、路径平滑、电机控制。

三层分工：
  Policy（业务决策）     → "锅把在这里，去抓" → 几个目标位姿
  Skill（动作分解）      → "抓需要：接近→到位→闭合→抬升" → 子步骤序列
  RobotDriver（轨迹执行） → "从关节角A平滑运动到关节角B" → 真正的轨迹规划

Skill 只有在需要把一个复杂的高级动作拆成多个子步骤并跟踪进度时才有用。如果只是单纯的"左臂移动到 A 点→闭合→移动到 B 点"这种线性步骤，可以直接走 API 路径（1个 Goal → 1个 MotionPrimitive），不需要写 Skill。
