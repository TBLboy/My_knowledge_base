## 1. Planner 内部这些属性是状态机吗？这种思维叫什么？

**不是严格意义上的状态机，但有状态机的成分。**

先区分两个东西：

```python
# 这是"任务上下文 / 元数据"
self._active_task_id         = "task_001"       # 当前在做什么任务
self._active_task_type       = "test_gripper"   # 当前任务类型
self._target_class           = ""               # 当前任务目标
self._policy                 = TestGripperPolicy # 当前任务的决策逻辑

# 这是状态机变量
self._world.robot_status.state  = RobotState.IDLE  # 真正的状态
```

关键区别：

| 类型 | 变量 | 是什么 |
|------|------|--------|
| **元数据/上下文** | `_active_task_id`, `_active_task_type`, `_target_class`, `_policy` | 记录"当前正在做什么任务"的上下文信息 |
| **状态机** | `robot_status.state`（IDLE / PREPARING_TASK / EXECUTING_TASK / PAUSED / SUCCESS / ERROR） | 明确枚举了系统处于什么工作阶段，并需要受控切换 |

`_pending_goal` 和 `_left_arm_busy` 也不是状态机，它们是**忙标志**（busy flags），更接近"信号量/锁"的思维。

**这种组织方式在工程上通常叫作"Orchestrator（编排器）模式"：**

> 一个中心节点持有当前工作上下文，定期检查能否继续推进，把每一步的具体决策委托给子组件（Policy），把执行委托给远程执行器（MotionExecutor）。

用你熟悉的概念类比：

```text
Orchestrator = TaskPlannerNode
  持有上下文（当前任务 ID、类型、策略）
  驱动调度（定时器 _on_tick）
  委托决策（Policy）
  委托执行（Action → MotionExecutor）
```

另一个常见的类比是 **"Master-Worker"（主-工作者）模式**：

```text
PlannerNode      = Master（规划调度）
MotionExecutor   = Worker（执行动作）
```

```text
Planner 说："下一步该做什么了？"
Policy 回答："该操作右臂了，张开手。"
Planner 封装成 goal → 发送给 MotionExecutor
Planner 等待回复
回复到达后 Planner 再次问 Policy："再下一步呢？"
```

所以 _active_task_id 这类属性的核心作用就是：**让这个循环在每次 _on_tick 触发时，知道自己正在处理哪个任务、处于哪个阶段**，这样才不会把不同任务的状态搞混。

## 2. 每个任务有自己的状态机吗？

**有，每个 Policy 内部维护了自己的"步骤状态机"。**

`TaskPlannerNode` 有一个统一的 `_policy`，但 `_policy` 指向的具体 Policy 实例是随着 `task_type` 变化的：

```text
test_gripper  → TestGripperPolicy  实例
cut_cucumber  → CutCucumberPolicy  实例
sweet_three   → SweetPolicy        实例
```

每个 Policy 内部都会追踪"已经执行到第几步了"。

以你读过的 `TestGripperPolicy` 为例：

```python
class TestGripperPolicy(BasePolicy):
    def __init__(self, max_loop=3):
        self._max_loop = max_loop
        self._cached_steps: Optional[List[PlannedStep]] = None

    def select_next_goal(self, ...):
        if self._cached_steps is None:
            self._cached_steps = self._create_steps()  # 生成 6 个步骤

        for step in self._cached_steps:
            if step.status in (PENDING, FAILED, IN_PROGRESS):
                if step.status != IN_PROGRESS:
                    step.status = IN_PROGRESS         # ← 标记"正在执行"
                return step                           # ← 返回这一步骤

        return None  # ← 所有步骤都完成了
```

它内部的状态是：

```text
_cached_steps[0]  status = IN_PROGRESS   ← 当前正在执行 "张开"
_cached_steps[1]  status = PENDING       ← 等待执行 "扎取"
_cached_steps[2]  status = PENDING
_cached_steps[3]  status = PENDING
_cached_steps[4]  status = PENDING
_cached_steps[5]  status = PENDING
```

MotionExecutor 执行完一个动作后，会回调 `policy.update_step_status()` 把对应步骤标记为 `COMPLETED` 或 `FAILED`：

```python
def _on_result(self, fut):
    ...
    if step_index is not None:
        self._policy.update_step_status(
            step_index=self._current_step_index,
            status=StepStatus.COMPLETED,   # 或 FAILED
            failure_reason=...,
        )
```

所以 Policy 内部相当于：

```text
一个步骤列表 + 当前执行指针 + 每个步骤的状态
```

这是一个**轻量级的步骤状态机**。

更复杂的 Policy（如 `SweetPolicy`）会维护更多状态：左右臂各自的步骤序列、双臂交替顺序等。但因为都继承自 `BasePolicy`，对外暴露的接口始终只有两个方法：

```python
select_next_goal(task_id, task_type, target_class)  # → 下一步
update_step_status(step_index, status, reason)       # ← 回调更新
```

## 3. `ExecuteTask.Goal` 是什么？

**`ExecuteTask` 是一个 ROS 2 Action 定义（`ExecuteTask.action`），而 `ExecuteTask.Goal` 就是这个 Action 的 Go al 部分**。

Action 文件由三个区域组成，用 `---` 分隔：

[`ExecuteTask.action`](/home/tbl/Project/boss_electrics/kitchen_robot_home/src/dexbot_interfaces/action/ExecuteTask.action:1)

```text
# Goal ← 这是"请求"（TaskPlanner 发送给 MotionExecutor 的内容）
string task_id
string task_type
TaskTarget target
...

---
# Result ← 这是"响应"（MotionExecutor 执行完成后返回给 TaskPlanner）
bool success
string error_msg
...

---
# Feedback ← 这是"进度更新"（执行过程中不断返回的信息）
string phase
float32 progress
```

ROS 2 会根据这个 `.action` 文件自动生成三个消息类：

```python
from dexbot_interfaces.action import ExecuteTask

ExecuteTask.Goal        # 请求消息
ExecuteTask.Result      # 响应消息
ExecuteTask.Feedback    # 进度消息
```

所以 `goal_msg = ExecuteTask.Goal()` 只是创建了一个 Goal 消息实例，然后逐一填充它的字段。

---

再回头看你问的这个函数：

```python
def _build_gripper_action_goal(self, step) -> ExecuteTask.Goal:
    # 1. 创建一个 TaskTarget（动作的具体参数）
    task_target = TaskTarget()
    task_target.task_id = self._active_task_id    # 关联到当前任务
    task_target.object_id = ""                     # 没有操作物体
    task_target.class_name = "gripper_action"      # 日志标识
    task_target.action_name = step.action_name     # "张开" 或 "扎取"
    task_target.arm_type = step.arm_type           # 0=左臂, 1=右臂

    # 2. 创建 ExecuteTask 的 Goal 消息
    goal_msg = ExecuteTask.Goal()
    goal_msg.task_id = self._active_task_id        # 关联到当前任务
    goal_msg.task_type = "gripper_action"           # ← MotionExecutor 按这个值路由
    goal_msg.target = task_target                   # ← 动作参数放在 target 里
    return goal_msg
```

整个动作的三层封装关系：

```text
ExecuteTask.Goal                      ← 发给 MotionExecutor 的"任务信封"
├── task_id = "task_001"              ← 信封上的任务编号
├── task_type = "gripper_action"      ← 信封上的"业务类型"（MotionExecutor 据此选 handler）
└── target = TaskTarget               ← 信封里的具体指令
    ├── action_name = "张开"           ← 做什么
    └── arm_type = 1                  ← 哪只手做
```

到了 MotionExecutor 端，当它收到这个 Goal 时：

```python
# motion_executor_node.py
async def _execute_task_cb(self, goal_handle):
    task_type = goal_handle.request.task_type.lower()   # "gripper_action"
    skill = self._skills.get(task_type)                  # 查字典 → 找 GripperActionApi
    ...
    ok = await self._execute_motion_primitive(motion_primitive)
```

这就是整个 **TaskPlanner 到 MotionExecutor 的通信契约**：`task_type` 是路由键，`TaskTarget` 是参数载荷。

`_build_gripper_action_goal` 把 Policy 生成的 `PlannedStep` 转换成了 MotionExecutor 能理解的消息格式。类似地，`_build_cartesian_goal` 把 `Pose3D` 填入 `TaskTarget.grasp_position/orientation`，`_build_pick_and_place_goal` 填入 `grasp_pose` 和 `place_pose` 两个位姿。它们都是把 Policy 的输出翻译成 ROS 消息。
