## 1. 项目概览

项目名：**ilflow（Imitation Learning Flow）**

这是一个基于 **Diffusion Policy** 的机器人模仿学习框架。它读取机器人示教数据，将图像、机器人状态作为条件，训练一个能够预测机器人动作序列的策略模型。

主要技术：

- Python 3.10
- PyTorch
- Hydra / OmegaConf 配置管理
- Zarr 数据集
- OpenCV、torchvision

项目的主线可以先记成：

```text
配置文件
   ↓
Dataset / DataLoader
   ↓
Builder 组装模型和训练工具
   ↓
DiffusionPolicy
   ↓
UniversalRunner 训练
```

## 2. 目录职责

```text
ilflow/
├── configs/              # 训练配置，例如 configs/dp.yaml
├── src/
│   ├── builder/          # 根据配置组装 DataLoader、Policy、Optimizer
│   ├── data/             # Zarr 数据读取、采样、padding、归一化
│   ├── engine/           # 训练循环和评估流程
│   ├── model/
│   │   ├── backbones/    # 视觉编码器、机器人状态编码器
│   │   ├── networks/     # 噪声预测网络，例如 DiffusionMLP
│   │   ├── schedulers/   # DDPM 调度器
│   │   └── components/   # 位置编码等基础组件
│   └── policy/           # DiffusionPolicy，封装算法逻辑
├── test/
│   └── train_dp.py       # 当前训练入口
└── utils/                # 维度解析、mock 数据生成等工具
```

### 2.1 Data 数据层

目录：`src/data/`

主要负责：

- 从 Zarr 文件读取 `action`、机器人状态和图像
- 根据时间窗口取出一段观测和动作
- 在 episode 边界进行 padding
- 对数据进行 downsample
- 对动作和状态做 normalization
- 将 NumPy 数据转换为 PyTorch Tensor

相关文件：

- `dataset.py`：协调整个取样流程
- `sampler.py`：计算要读取哪些时间索引
- `padding.py`：处理窗口不足时的填充
- `normalizer.py`：计算和应用归一化统计量

### 2.2 Model 模型层

模型层由多个零件组成：

- `backbones/`：把图像和机器人状态转换成特征向量
- `networks/`：根据带噪动作、时间步和观测条件预测噪声
- `schedulers/`：实现 DDPM 的加噪和去噪数学过程
- `components/`：提供时间编码等通用组件

### 2.3 Policy 策略层

核心文件：`src/policy/diffusion_policy.py`

它不是单独的一层神经网络，而是一个完整的算法对象，负责：

- 组织视觉编码器、状态编码器、噪声预测网络和 DDPM Scheduler
- 实现训练损失 `compute_loss(batch)`
- 实现推理动作生成 `get_action(batch)`

可以把它理解成 Diffusion Policy 的“大脑”。

### 2.4 Engine 执行层

核心文件：`src/engine/trainer.py`

`UniversalRunner` 负责通用训练循环，例如：

- 遍历 epoch 和 batch
- 将 batch 搬到设备
- 调用 `policy.compute_loss(batch)`
- 执行反向传播
- 调用 `optimizer.step()` 更新参数
- 更新学习率
- 记录 loss

Trainer 不需要知道 Diffusion Policy 的内部细节。因此，只要新的 Policy 继续提供同样的接口：

```python
loss = policy.compute_loss(batch)
```

就不需要修改 `trainer.py`。

## 3. Dataset、DataLoader 和 Sample 的关系

### 3.1 什么是一个 sample？

在监督学习中，可以先用一个简单公式理解：

```text
一个 sample = feature + label
```

在这个项目中，一个 sample 不是单个图片，而是一段时间窗口的数据，包含：

- 历史图像观测 `img_global`
- 历史机器人状态 `robot_qpos`
- 未来动作序列 `action`

例如配置中：

```yaml
obs_horizon: 2
pred_horizon: 4
action_dim: 8
state_dim: 7
```

一个 sample 大致可以表示为：

```text
img_global:  [2, 3, 32, 32]  # 最近 2 帧 RGB 图像
robot_qpos:  [2, 7]           # 最近 2 个时间步的机器人状态
action:      [4, 8]           # 未来 4 步动作，每步 8 维
```

这里可以把：

- `img_global` 和 `robot_qpos` 看作 feature / condition
- `action` 看作训练目标 label

### 3.2 什么是 Dataset？

多个 sample 加上“如何读取 sample 的规则”，就是一个 Dataset。

Dataset 至少提供两个基本能力：

```python
len(dataset)       # 一共有多少个 sample
dataset[i]         # 读取第 i 个 sample
```

本项目中的 `ZarrDataset` 负责：

1. 找到当前索引属于哪个 episode
2. 读取动作和观测的时间窗口
3. 调用 sampler 进行时间索引计算
4. 调用 padder 处理边界
5. 调用 normalizer 处理动作和状态
6. 将图像从 HWC 转换为 PyTorch 使用的 CHW
7. 返回一个包含三个字段的字典

```python
{
    "action": action_tensor,
    "robot_qpos": state_tensor,
    "img_global": image_tensor,
}
```

### 3.3 什么是 DataLoader？

DataLoader 可以理解为：

```text
Dataset + batch 规则 + 加载规则 = DataLoader
```

它在 Dataset 的基础上负责：

- 一次取出多个 sample，组成一个 batch
- 是否打乱数据 `shuffle`
- 使用多少个进程加载数据 `num_workers`
- 是否提前预取数据 `prefetch_factor`
- 是否使用锁页内存 `pin_memory`

例如单个 sample 的 `action` 是 `[4, 8]`，batch size 为 8 后，Trainer 收到的就是：

```text
action:      [8, 4, 8]
robot_qpos:  [8, 2, 7]
img_global:  [8, 2, 3, 32, 32]
```

## 4. 配置文件控制什么？

配置文件：`configs/dp.yaml`

它集中定义了训练需要的参数，代码通过配置来决定具体使用什么模型和超参数。

当前关键配置包括：

```yaml
state_dim: 7
action_dim: 8
obs_horizon: 2
pred_horizon: 4
action_horizon: 2
vision_backbone: resnet18
noise_netwok: mlp
num_train_steps: 100
```

这些参数的含义：

- `state_dim`：每个时间步的机器人状态维度
- `action_dim`：每个时间步的动作维度
- `obs_horizon`：输入多少个历史观测时间步
- `pred_horizon`：模型预测多少个未来动作时间步
- `action_horizon`：预测后实际执行多少步，再重新规划
- `vision_backbone`：使用哪个视觉编码器
- `noise_netwok`：使用哪个噪声预测网络
- `num_train_steps`：扩散训练的总时间步数

## 5. Builder 工厂思维

这个项目使用了“配置 + Builder + 组件”的工程化思路。

Builder 只负责**装配对象**，具体装配什么由配置文件决定。这样更换模型、优化器或数据加载方式时，主训练流程不需要大改。

### 5.1 `data_builder.py`

作用：构建 DataLoader。

主要步骤：

1. 读取或计算数据归一化统计量
2. 创建 `ZarrDataset`
3. 使用配置中的 batch size、worker 数量等参数创建 `DataLoader`

输出：

```python
dataloader
```

### 5.2 `policy_builder.py`

作用：组装完整的 `DiffusionPolicy`。

它依次创建：

1. 视觉编码器，例如 `ResNetBackbone`
2. 机器人状态编码器 `RobotStateEncoder`
3. DDPM Scheduler
4. 噪声预测网络 `DiffusionMLP`
5. 将这些零件传给 `DiffusionPolicy`

输出：

```python
policy
```

### 5.3 `optim_builder.py`

作用：构建优化器和学习率调度器。

当前支持：

- 优化器：AdamW、Adam、SGD
- 学习率调度器：CosineAnnealingLR

它会从 `policy.parameters()` 中筛选出 `requires_grad=True` 的参数，只更新需要训练的部分。

### 5.4 三个 Builder 的整体关系

```python
policy = build_policy(cfg_global)
optimizer, scheduler = build_optimizer_and_scheduler(cfg_global, policy)
dataloader = build_data(cfg_global)
```

可以把它们分别理解成：

```text
data_builder      备好数据
policy_builder    组装模型
optim_builder     配好模型训练工具
```

主入口只负责调用它们，不负责手动创建每一个网络层和数据处理对象。

## 6. 训练入口和调用链

入口文件：`test/train_dp.py`

当前调用链：

```text
test/train_dp.py
    ↓
build_policy(cfg)
    ↓
build_optimizer_and_scheduler(cfg, policy)
    ↓
build_data(cfg)
    ↓
UniversalRunner(...)
    ↓
runner.run()
    ↓
for batch in dataloader
    ↓

    ↓

```

其中 Builder 负责“准备”，Runner 负责“循环执行”，Policy 负责“具体算法”。

## 7. DiffusionPolicy 的职责

文件：`src/policy/diffusion_policy.py`

```python
class DiffusionPolicy(nn.Module):
```

它继承 `nn.Module`，因此可以正常使用 PyTorch 的标准能力：

```python
policy.to(device)
policy.train()
policy.eval()
policy.parameters()
policy.state_dict()
```

初始化时，它接收 Builder 已经创建好的组件：

```python
DiffusionPolicy(
    vision_encoder,
    state_encoder,
    network,
    scheduler,
    dims,
)
```

这些组件会保存为：

```text
DiffusionPolicy
├── vision_encoder
├── state_encoder
├── network
└── scheduler
```

使用 `self.vision_encoder`、`self.state_encoder`、`self.network` 保存子网络很重要，因为 PyTorch 会自动注册它们，使得：

- `policy.parameters()` 能收集所有子网络参数
- `policy.to(device)` 能把子网络一起搬到 CPU 或 GPU
- `policy.state_dict()` 能保存完整模型

## 8. `compute_loss(batch)` 训练流程

### 8.1 总体思路

Diffusion Policy 的训练目标不是直接从图像回归动作，而是：

1. 取出真实动作序列
2. 生成一份已知的随机噪声
3. 随机选择一个扩散时间步
4. 给真实动作加噪
5. 让网络根据带噪动作、时间步和观测条件预测噪声
6. 比较预测噪声和真实噪声

核心目标可以写成：

```text
预测噪声 ≈ 实际加入的噪声
```

### 8.2 第一步：读取 batch

源码从 batch 中读取：

```python
actions = batch["action"]
img = batch["img_global"]
qpos = batch["robot_qpos"]
B = actions.shape[0]
```

典型形状：

```text
actions: [B, pred_horizon, action_dim] = [8, 4, 8]
img:     [B, obs_horizon, C, H, W]       = [8, 2, 3, 32, 32]
qpos:    [B, obs_horizon, state_dim]     = [8, 2, 7]
```

含义：

- `B=8`：一次处理 8 个 sample
- `pred_horizon=4`：每个 sample 有未来 4 步动作
- `action_dim=8`：每一步动作有 8 个数
- `obs_horizon=2`：每个 sample 使用最近 2 步观测

### 8.3 第二步：编码观测条件

图像和机器人状态的原始形状不同，不能直接送入 MLP，因此需要先编码：

```python
vision_feat = self.vision_encoder(img)
state_feat = self.state_encoder(qpos)
global_cond = torch.cat([vision_feat, state_feat], dim=-1)
```

数据流：

```text
img
  ↓ vision_encoder
vision_feat

qpos
  ↓ state_encoder
state_feat

vision_feat + state_feat
  ↓ torch.cat
global_cond
```

`global_cond` 就是当前环境和机器人状态的综合描述，后面的噪声预测网络依靠它来决定应该生成什么动作。

### 8.4 第三步：生成噪声并加噪

```python
noise = torch.randn_like(actions)
t = torch.randint(
    0,
    self.scheduler.timesteps,
    (B,),
    device=actions.device,
)
noisy_actions = self.scheduler.add_noise(actions, noise, t)
```

`noise` 和 `actions` 形状相同：

```text
actions: [B, pred_horizon, action_dim]
noise:   [B, pred_horizon, action_dim]
```

`t` 为每个 sample 随机选择一个扩散时间步。例如：

```text
t = [5, 72, 13, 99, ...]
```

同一个 batch 中不同 sample 可以处在不同噪声程度。通常时间步越大，动作中的噪声越多。

Scheduler 根据 `t` 将真实动作和噪声组合成 `noisy_actions`：

```text
真实动作 + 已知噪声 + 时间步
          ↓ scheduler.add_noise()
       带噪动作
```

因为噪声是代码自己生成的，所以训练时知道正确答案是什么。

### 8.5 第四步：展开动作并预测噪声

当前噪声预测网络是 MLP，需要把动作序列展开：

```python
noisy_flat = noisy_actions.view(B, -1)
```

形状从：

```text
[B, pred_horizon, action_dim]
```

变成：

```text
[B, pred_horizon * action_dim]
```

以当前配置为例：

```text
[8, 4, 8] → [8, 32]
```

源码中的 `(8, 28)` 注释与配置不一致，属于注释错误；因为 `4 × 8 = 32`。

然后调用噪声预测网络：

```python
pred_noise = self.network(
    noisy_flat,
    t,
    global_cond,
)
```

网络的三个输入分别表示：

- `noisy_flat`：当前动作被污染成什么样
- `t`：当前处于哪个扩散阶段
- `global_cond`：机器人看到的环境和自身状态

输出应为：

```text
pred_noise: [B, pred_horizon * action_dim]
```

### 8.6 第五步：计算 MSE Loss

```python
return F.mse_loss(
    pred_noise,
    noise.view(B, -1),
)
```

真实噪声也被展开成 `[B, pred_horizon * action_dim]`，然后和预测噪声计算均方误差：

```text
MSE(预测噪声, 真实噪声)
```

Loss 越小，表示模型越能够根据带噪动作、扩散时间步和观测条件识别出加入的噪声。

## 10. 当前源码结论

### 已确认

- `trainer.py` 只依赖 `policy.compute_loss(batch)` 接口，因此新的 Policy 只要遵守该接口，Trainer 就可以复用。
- `DiffusionPolicy` 是算法组织层，不只是一个单独的神经网络。
- `compute_loss()` 的训练主流程是：编码条件 → 随机加噪 → 预测噪声 → MSE。
- `Dataset` 负责定义如何读取单个 sample；`DataLoader` 负责组 batch 和加载策略。
- 三个 Builder 分别负责构建 DataLoader、Policy、Optimizer/Scheduler。
- 配置文件集中管理模型、数据、扩散过程和训练参数。

### 当前发现的问题

- `ModelDims` 在 `diffusion_policy.py` 中被导入，但当前没有直接使用。
- `noisy_flat` 的源码注释写成 `(8, 28)`，当前配置下实际应为 `(8, 32)`。
- `get_action()` 中将动作维度硬编码为 `7`，但配置中的 `action_dim` 是 `8`。
- `__init__()` 中 `self.normalizer` 被注释掉，但 `get_action()` 仍然调用 `self.normalizer.unnormalize()`。
- 配置中有 `eval_freq` 和 `save_freq`，但当前训练流程中的评估和模型保存逻辑还不完整。
- Data schema 注释仍待补充，不同数据集格式可能需要不同 Dataset 实现。

## 12. Zarr 数据管线的详细流程

### 12.1 Zarr 数据的基本结构

当前 mock 数据使用下面的结构：

```text
dataset.zarr/
├── data/
│   ├── action          # [总时间步数, action_dim]
│   ├── robot_qpos      # [总时间步数, state_dim]
│   └── img_global      # [总时间步数, H, W, C]
└── meta/
    └── episode_ends    # 每个 episode 在全局数组中的结束位置
```

数据被保存成“所有 episode 首尾相接的一条大数组”，`episode_ends` 用来告诉 Dataset 每个 episode 在哪里结束。

例如：

```text
episode_ends = [20, 40]

episode 0: 全局索引 [0, 20)
episode 1: 全局索引 [20, 40)
```

这里的结束位置采用 Python / Zarr 常见的左闭右开语义，索引 20 属于下一个 episode。

### 12.2 `SampleSpec`：只描述“怎么读”

文件：`src/data/sampler.py`

`SampleSpec` 是一个很小的数据类，只保存 Zarr 切片需要的三个参数：

```python
SampleSpec(
    slice_start,
    slice_end,
    slice_step,
)
```

它不负责真正读取数据，只负责描述：

```text
从哪里开始读，到哪里结束，每隔几帧读一次
```

这样 Sampler 和 Dataset 的职责被分开：

- Sampler：计算索引
- Dataset：拿着索引去读 Zarr

### 12.3 `SequenceSampler` 如何取动作窗口

动作窗口从当前时间点开始，向未来取 `pred_horizon` 个时间步：

```text
[current_idx,
 current_idx + stride,
 ...,
 current_idx + (pred_horizon - 1) * stride]
```

对应配置：

```yaml
pred_horizon: 4
downsample_ratio: 1.0
```

理想情况下，一个动作窗口包含：

```text
[t, t+1, t+2, t+3]
```

`sample_action()` 最终只返回 `SampleSpec`，实际读取由 Dataset 的 `_read_zarr()` 完成。

### 12.4 `SequenceSampler` 如何取观测窗口

观测窗口以当前时间点为结束点，向历史取 `obs_horizon` 个时间步：

```text
[t - (obs_horizon - 1) * stride, ..., t]
```

例如：

```text
obs_horizon = 2
当前时间点 t = 10
观测窗口 = [9, 10]
```

如果当前时间点位于 episode 开头，理论起点可能小于 episode 起点。Sampler 会把读取起点钳制到 episode 起点，后面再由 Padder 补齐缺少的历史帧。

### 12.5 `ZarrDataset._create_indices()` 的作用

Dataset 初始化时不会把所有样本真正读入内存，而是先创建一张“可用全局索引表”。

它会遍历每个 episode，并丢弃那些无法提供完整未来动作窗口的时间点：

```text
valid_len = episode_len - (pred_horizon - 1) * stride
```

这样做的结果是：

- episode 尾部不会跨到下一个 episode 取动作
- `len(dataset)` 返回的是可用窗口数量，而不是原始总帧数
- DataLoader 只会从合法的窗口起点中采样

观测窗口在 episode 开头可以通过左侧 padding 解决；动作窗口则通常在索引阶段直接排除尾部不完整样本。

### 12.6 `ZarrDataset.__getitem__()` 的真实顺序

读取一个 sample 时，实际顺序是：

```text
全局索引
   ↓
确定所属 episode
   ↓
SequenceSampler 计算 action / observation 的切片
   ↓
从 Zarr 读取 NumPy 数组
   ↓
DataPadder 补齐时间维度
   ↓
LinearNormalizer 归一化 action / state
   ↓
图像除以 255，并从 HWC 转为 CHW
   ↓
返回字典
```

最终返回：

```python
{
    "action": [pred_horizon, action_dim],
    "robot_qpos": [obs_horizon, state_dim],
    "img_global": [obs_horizon, C, H, W],
}
```

### 12.7 `DataPadder` 的三种模式

文件：`src/data/padding.py`

Padder 只在时间维度上填充，不改变每一帧内部的维度。

支持：

| 模式 | 行为 | 适合场景 |
|---|---|---|
| `edge` | 重复边界帧 | 当前配置默认模式 |
| `zero` | 补零 | 需要配合 mask 的 RNN / Transformer |
| `wrap` | 循环取另一端数据 | 周期性数据 |

当前观测一般在左侧补齐。例如 episode 第一个时间点缺少上一帧时：

```text
原始观测: [frame_0]
edge padding 后: [frame_0, frame_0]
```

### 12.8 `LinearNormalizer` 的归一化方式

文件：`src/data/normalizer.py`

系统会扫描 Zarr 中除图像之外的数组，为每个维度计算：

- `min`
- `max`
- `scale`
- `offset`

归一化公式：

```text
x_norm = (x - offset) * scale
scale  = 2 / (max - min)
offset = (max + min) / 2
```

目标范围是 `[-1, 1]`。

反归一化公式：

```text
x_original = x_norm / scale + offset
```

如果某个 key 没有统计量，Normalizer 会原样返回。图像不走这个 min-max 统计，而是在 Dataset 中直接：

```python
image = image.float() / 255.0
```

Normalizer 还提供 `state_dict()` 和 `load_state_dict()`，说明归一化参数应该和模型一起保存，推理时必须使用训练数据对应的统计量。

## 13. 条件编码器和噪声预测网络

### 13.1 `BaseConditionEncoder`

文件：`src/model/backbones/base_condition_encoder.py`

这是一个抽象接口，规定条件编码器需要实现：

```python
forward(x)
```

它本身没有具体网络，作用是统一视觉编码器、状态编码器等组件的接口。

### 13.2 `ResNetBackbone`：逐帧处理图像

文件：`src/model/backbones/resnet.py`

ResNet 原本只接受四维图像：

```text
[N, C, H, W]
```

但 Dataset 返回的是带历史时间维度的五维数据：

```text
[B, T, C, H, W]
```

因此 ResNetBackbone 使用“折叠时间维”的办法：

```text
[B, T, C, H, W]
        ↓ view
[B*T, C, H, W]
        ↓ ResNet
[B*T, 512]
        ↓ projector
[B*T, vision_out_dim]
        ↓ reshape
[B, T*vision_out_dim]
```

当前配置中：

```text
B = 8
T = 2
vision_out_dim = 64

输出 = [8, 2*64] = [8, 128]
```

ResNet 的最后分类层被去掉，只保留图像特征提取部分，然后通过一个线性层把 512 维特征投影到配置指定的 `vision_out_dim`。

### 13.3 `RobotStateEncoder`：逐时间步处理机器人状态

文件：`src/model/backbones/robot_state_encoder.py`

它使用配置动态创建 MLP：

```yaml
state_dim: 7
state_hidden_dims: [256, 128]
state_out_dim: 64
```

对应网络大致是：

```text
7 → Linear(256) → ReLU
  → Linear(128) → ReLU
  → Linear(64)
```

输入：

```text
[B, T, state_dim]
```

和图像编码器一样，它先折叠时间维：

```text
[B, T, 7]
    ↓
[B*T, 7]
    ↓ MLP
[B*T, 64]
    ↓
[B, T*64]
```

当前配置下输出是 `[8, 128]`。

### 13.4 时间步编码

文件：`src/model/components/pos_transform.py`

扩散网络必须知道当前的时间步 `t`，因为不同时间步代表不同噪声程度。

项目中有两个时间编码类：

- `TimeEmb`：较简单的 `sin(t * position)` 编码，被旧版 `MLPNetwork` 使用
- `SinusoidalPosEmb`：标准正弦/余弦位置编码，被当前 `DiffusionMLP` 使用

当前 DiffusionMLP 的时间编码流程是：

```text
t: [B]
  ↓ SinusoidalPosEmb
[B, time_in_dim]
  ↓ Linear + Mish + Linear
[B, time_out_dim]
```

### 13.5 `DiffusionMLP`：把三个输入拼起来

文件：`src/model/networks/diffusion_mlp.py`

这是当前 Builder 实际使用的噪声预测网络。

它先把时间步编码成向量，再将三个输入直接拼接：

```python
x = torch.cat(
    [noisy_action, t_emb, global_cond],
    dim=-1,
)
```

三个输入的含义：

```text
noisy_action  当前带噪动作
t_emb         当前扩散时间步的编码
global_cond   图像特征 + 机器人状态特征
```

当前配置下，各维度是：

```text
noisy_action: [8, 32]
t_emb:        [8, 64]
global_cond:  [8, 256]
网络输入:     [8, 352]
```

MLP 隐藏层由配置决定：

```yaml
noise_hidden_dims: [256, 128]
```

因此当前网络结构近似为：

```text
352 → Linear(256) → ReLU
    → Linear(128) → ReLU
    → Linear(32)
```

最后输出 `flat_action_dim=32`，与真实噪声展平后的形状一致。

### 13.6 `MLPNetwork`：旧版或备用网络

文件：`src/model/networks/mlp.py`

这个类也实现了：

```python
forward(noisy_action, t, cond)
```

但当前 `policy_builder.py` 选择的是 `DiffusionMLP`，没有使用 `MLPNetwork`。

它的设计更简单：把 `noisy_action`、`cond` 和 `TimeEmb(t)` 拼接，再经过固定的两层 256 维 MLP，输出 `action_dim`。

因此它更像早期版本或备用实现。当前主流程的维度逻辑应以 `DiffusionMLP + ModelDims` 为准。

## 14. 维度解析和 DDPM Scheduler

### 14.1 `ModelDims`：集中管理形状

文件：`utils/dim_parser.py`

Diffusion Policy 中最容易出错的地方就是维度。`ModelDims` 把这些派生维度集中算出来，避免每个模块重复手算。

当前配置下：

```text
action_dim       = 8
pred_horizon     = 4
flat_action_dim  = 8 * 4 = 32

vision_out_dim   = 64
obs_horizon      = 2
flat_vision_dim  = 64 * 2 = 128

state_out_dim    = 64
flat_state_dim   = 64 * 2 = 128

time_out_dim     = 64

network_input_dim = 32 + 128 + 128 + 64 = 352
```

这些维度对应：

```text
DiffusionMLP 输入 = 带噪动作 + 图像条件 + 状态条件 + 时间条件
```

`align_coef()` 则解决另一个问题：扩散系数只有 `[B]`，但动作可能是 `[B, T, D]`。它会把系数自动 reshape 成：

```text
[B] → [B, 1, 1]
```

从而可以和动作张量进行广播相乘。

### 14.2 `DDPMScheduler` 的职责

文件：`src/model/schedulers/ddpm_scheduler.py`

Scheduler 不是神经网络，没有需要训练的参数。它只负责扩散过程的数学计算：

- 训练时通过 `add_noise()` 加噪
- 推理时通过 `step()` 逐步去噪

初始化时，它根据 beta 序列预计算：

```text
betas
alphas = 1 - betas
alphas_cumprod
sqrt_alphas_cumprod
sqrt_one_minus_alphas_cumprod
```

预计算的目的是避免每个 batch 重复计算。

### 14.3 前向扩散：`add_noise()`

前向扩散公式：

```text
x_t = sqrt(alpha_bar_t) * x_0
    + sqrt(1 - alpha_bar_t) * noise
```

其中：

- `x_0`：真实动作
- `noise`：随机高斯噪声
- `t`：扩散时间步
- `x_t`：加噪后的动作

在代码中，先根据每个 sample 的 `t` 取出对应系数，再用 `align_coef()` 对齐到动作张量的维度。

### 14.4 反向扩散：`step()`

推理时从纯噪声开始，时间步从大到小循环：

```text
x_T → x_(T-1) → ... → x_1 → x_0
```

每一步：

1. 根据当前时间步取得 `beta_t`、`alpha_t` 等系数
2. 使用网络预测的噪声计算 `x_(t-1)` 的均值
3. 当 `t > 0` 时加入随机方差
4. 返回下一步样本

当前实现使用了简化的方差：

```python
sigma_t = sqrt(beta_t)
```

它能表达基本的 DDPM 去噪流程，但不是完整工业实现中的所有后验方差细节。

## 15. 训练器和优化器的实际行为

### 15.1 `UniversalRunner`

`UniversalRunner.run()` 的每个 batch 实际执行：

```text
batch 搬到 device
    ↓
policy.compute_loss(batch)
    ↓
optimizer.zero_grad()
    ↓
loss.backward()
    ↓
optimizer.step()
```

每个 epoch 结束后，如果存在学习率调度器，再调用一次：

```python
self.lr_scheduler.step()
```

所以当前 scheduler 是“每个 epoch 更新一次”，不是每个 optimizer step 更新一次。

文件中还保留了一个较早的 `Runner` 类。它功能更简单，没有 device 搬运、学习率调度和 tqdm，目前主入口使用的是 `UniversalRunner`。

### 15.2 `optim_builder.py`

优化器从 Policy 的全部可训练参数中筛选参数：

```python
params = [
    p for p in model.parameters()
    if p.requires_grad
]
```

当前配置：

```yaml
optimizer:
  name: adamw
  lr: 1.0e-4
  weight_decay: 1.0e-6
  betas: [0.95, 0.999]
```

会构建 `AdamW`。

学习率调度器当前支持：

```yaml
scheduler:
  name: cosine
  min_lr: 1.0e-6
```

会构建 `CosineAnnealingLR`，周期设置为训练 epoch 数。

配置中的 `warmup_steps` 目前只是预留字段，代码没有实现 warmup。

## 17. 剩余源码中的重要不一致

下面这些是继续阅读后确认的实现风险：

### 数据和配置

- `downsample_ratio` 在配置中写成 `1.0`，但 `ZarrDataset` 使用 `getattr(cfg_global.downsample_ratio, 'downsample_ratio', 1)` 读取，非 1 的配置可能不会按预期生效。
- `SequenceSampler` 的 `slice_step` 和 `_create_indices()` 更适合整数 stride；当前配置通过默认值退回到整数 `1`，这一行为需要明确。
- `action_horizon` 被读取并保存，但当前 sampler 和训练流程没有真正使用它。RHC 的“只执行前几步”还没有落到执行代码中。
- `DataLoader` 固定设置 `prefetch_factor=2` 和 `persistent_workers=True`，如果以后把 `num_workers` 配为 `0`，需要额外处理，否则 PyTorch DataLoader 配置可能报错。

### 模型和配置

- `vision_backbone` 的配置注释声称支持多个 backbone，但当前 Builder 实际只实现 `resnet18`。
- `pretrained: "true"` 当前没有真正生效，ResNet 使用的是 `weights=None`，即不加载预训练权重。
- `frozen=True` 只冻结了 ResNet backbone 参数，但 `policy.train()` 可能再次把 backbone 切回 train 模式，冻结 BatchNorm 统计量的意图需要单独确认。
- `vision_hidden_dim=512` 是 ResNet 投影前维度；实际进入条件向量的是 `vision_out_dim=64`。源码中部分旧注释仍使用 `256`，需要以真实配置和代码为准。
- `beta_schedule` 当前没有参与 Scheduler 构建，实际始终使用线性 `torch.linspace` beta schedule。
- `num_inference_steps` 当前没有参与推理循环，`get_action()` 使用的是 `scheduler.timesteps`。
- `DDPMScheduler` 不是 `nn.Module`，所以 `policy.to(device)` 不会自动搬运 Scheduler 内部的 beta 和 alpha 张量。配置 device、Runner device 必须保持一致。

### 训练和推理

- `UniversalRunner` 的类注释提到保存模型，但当前代码没有 checkpoint 保存逻辑。
- 配置中的 `eval_freq` 和 `save_freq` 尚未接入 `UniversalRunner`。
- `src/engine/evaluator.py` 当前为空文件，评估流程还没有实现。
- 训练过程存在多个 `print()` 调试输出，每个 batch 都会打印形状，正式训练时会产生大量日志。
- `train_dp.py` 使用相对当前工作目录的配置路径 `../configs/dp.yaml`，从不同目录启动脚本可能找不到配置。
- `train_dp.py` 中的 device 由 CUDA 自动检测决定，但 `build_policy()` 和 Scheduler 使用的是配置中的 `cfg_global.device`，两者可能不一致。
- `get_action()` 仍然依赖未注入的 `self.normalizer`，并且把 `action_dim` 硬编码为 7，当前推理链尚未达到可直接运行状态。

## 18. 当前全局认识

现在可以用下面这句话概括整个工程：

> ilflow 把 Zarr 中按 episode 存储的机器人示教数据切成固定时间窗口，分别编码历史图像和机器人状态，再把真实未来动作加上随机噪声，让一个以观测条件为输入的 MLP 学习预测这份噪声；训练循环本身由通用 Runner 完成，模型和数据对象由配置驱动的 Builder 组装。

对应的职责边界是：

```text
ZarrDataset       负责“一个 sample 怎么读出来”
DataLoader         负责“多个 sample 怎么组成 batch”
Encoder            负责“观测怎么变成特征”
Scheduler          负责“动作怎么加噪 / 去噪”
DiffusionMLP       负责“根据输入预测噪声”
DiffusionPolicy    负责“把这些步骤组织成算法”
UniversalRunner    负责“反复训练并更新参数”
Builder            负责“根据配置创建以上对象”
```

## 19. 下一步源码阅读顺序

剩余的主要学习重点已经从“文件职责”进入“算法细节”：

1. 手算一次 `ModelDims` 的所有维度，并对照 `DiffusionMLP` 的 Linear 层
2. 结合公式阅读 `DDPMScheduler.add_noise()` 和 `step()`
3. 用 mock 数据实际跑通一次 Dataset，打印一个 sample 的所有 shape
4. 修正或确认 `downsample_ratio`、device、normalizer 和 action dimension 等推理前置问题
5. 最后再阅读 `get_action()`，补齐训练和推理之间的差异
